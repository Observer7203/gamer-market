ЗАДАЧА 1
Частичная выдача заказа
------------------------------------------------------------------------------

Требование: заказ из нескольких позиций, часть которых выдать не удалось.
Выданное остаётся у покупателя, за невыданное возвращаются деньги, сумма
всегда сходится, любой шаг повторяем без лишних выдач и возвратов, а заказ
приходит в конечное состояние даже после обрыва процесса посреди выдачи.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Раздел 3 — воспроизводимый скрипт.
Разделы 4-8 — ручной прогон сценариев.

Все команды выполняются из корня проекта при поднятом окружении.
После изменения кода выдачи обязателен перезапуск фоновых процессов:

    docker compose restart worker scheduler


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Позиция — единица выдачи
~~~~~~~~~~~~~~~~~~~~~~~~

Раньше товар был свойством заказа: колонка orders.sku. При нескольких
позициях такая колонка либо хранит один артикул из многих, либо дублирует
данные, которые тут же расходятся. Артикул переехал в order_items, где ему
и место.

    order_items  order_id, position, sku, price_minor, currency,
                 status, created_at, settled_at
                 PRIMARY KEY (order_id, position)

Номер позиции назначается при создании по порядку и больше не меняется.
На нём построен идентификатор запроса к поставщику
(req_<заказ>_<позиция>_<поставщик>_g<поколение>), поэтому изменение номера
означало бы вторую выдачу.

Существующие заказы миграция перенесла как позицию номер 1: старые данные
читаются без исключений.

Каждая единица товара — отдельная позиция. Поле quantity в запросе
разворачивается в несколько позиций, потому что у каждой единицы свой код,
свой поставщик и свой исход.

Сумма заказа хранится в orders.price_minor и обязана равняться сумме
позиций. Это не соглашение, а отложенный триггер order_items_total_check:
транзакция, нарушившая равенство, не фиксируется.


Состояния позиции
~~~~~~~~~~~~~~~~~

    pending       создана, оплата ещё не подтверждена
    delivering    взята в работу исполнителем
    delivered     код выдан покупателю              конечное
    out_of_stock  у поставщиков нет товара          восстановимое
    failed        поставщики ответили отказом       восстановимое
    unresolved    ответа не было                    требует разрешения
    refunded      деньги возвращены                 конечное

Из out_of_stock и failed позиция возвращается в работу повтором либо
завершается возвратом денег.

Из unresolved возврат запрещён. Поставщик мог выдать код, и возврат денег
вместе с работающим товаром — прямой убыток. Неопределённость разрешается
только повтором к тому же поставщику с тем же идентификатором запроса.
Запрет выражен в таблице переходов OrderItem, а не проверкой в сервисе.


Состояние заказа — производная
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    delivered            выданы все позиции
    partially_delivered  часть выдана, за остальные возвращены деньги
    refunded             не выдана ни одна, возвращено всё

Источник правды — позиции. Статус заказа хранится отдельным полем ради
простых запросов и пересчитывается одним условным обновлением в
FinalizeOrder:

    UPDATE orders o
       SET status = CASE
             WHEN s.delivered = s.total THEN 'delivered'
             WHEN s.delivered = 0       THEN 'refunded'
             ELSE 'partially_delivered'
           END
      FROM (SELECT count(*) AS total,
                   count(*) FILTER (WHERE status = 'delivered')   AS delivered,
                   count(*) FILTER (WHERE settled_at IS NULL)     AS unsettled
              FROM order_items WHERE order_id = ?) s
     WHERE o.id = ? AND s.unsettled = 0 AND o.status IN ('paid', 'delivering')

Пока есть незавершённая позиция, оператор не меняет ничего. Повторно он
тоже не меняет ничего: заказ уже вышел из paid и delivering. Поэтому его
безопасно вызывать после каждой выдачи, после каждого возврата и из
восстановителя — сколько угодно раз.


Возврат денег
~~~~~~~~~~~~~

Решение о возврате принимает DeliverOrderItem, когда позиция исчерпала
бюджет попыток (delivery.give_up_after, по умолчанию 3 захода в работу)
и при этом состояние поставщика известно.

Однократность возврата обеспечена условием самого обновления:

    UPDATE order_items
       SET status = 'refunded', settled_at = now()
     WHERE order_id = ? AND position = ? AND status IN ('out_of_stock', 'failed')
 RETURNING price_minor, currency

Вторая попытка не находит строки и проводки не создаёт. Проверка «а не
возвращали ли уже» перед записью этого не дала бы: между чтением и записью
успевает вклиниться другой процесс.


Деньги
~~~~~~

В журнале появился четвёртый счёт — refund. Проводки:

    оплата    settlement +сумма заказа,  obligation −сумма заказа
    выдача    obligation +цена позиции,  revenue    −цена позиции
    возврат   obligation +цена позиции,  refund     −цена позиции

Идентификаторы проводок детерминированы и выводятся из факта, а не из
момента записи:

    pay_<event_id>            оплата
    deliver_<order_id>_<pos>  выдача позиции
    refund_<order_id>_<pos>   возврат позиции

Повторная запись того же факта отсекается уникальным индексом на паре
(txn_id, account) — это второй слой защиты после условного обновления.

Тождество, которое выполняется всегда:

    оплачено = выдано + возвращено + ещё в работе

В журнале оно выражено тем, что сумма всех счетов равна нулю, а остаток
obligation равен стоимости незавершённых позиций. Ноль охраняется
отложенным триггером: несбалансированная проводка не фиксируется.


Конечное состояние после обрыва
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Процесс может остановиться между занятием позиции и записью результата.
Позиция остаётся в delivering, строка выдачи — в in_flight, и без
вмешательства её не возьмёт ни один исполнитель.

Восстановитель HealStuckOrders делает пять вещей, каждая идемпотентна:

    released_jobs      возвращает в очередь задачи, брошенные исполнителем
    released_items     освобождает позиции, занятые дольше аренды (5 минут),
                       переводя их в unresolved
    applied_events     применяет платёжные события, пришедшие раньше заказа
    requeued_items     ставит в очередь незавершённые позиции без задачи
    finalized_orders   доводит до конечного статуса заказы, все позиции
                       которых завершены

Освобождённая позиция переводится в unresolved, а не в pending: исполнитель
мог упасть уже после того, как поставщик выдал код. Повтор обратится к тому
же поставщику с тем же идентификатором и получит тот же код.


Изменения в API
~~~~~~~~~~~~~~~

Создание заказа принимает состав:

    {"items": [{"sku": "KEY-GTA5"}, {"sku": "KEY-CS2", "quantity": 2}]}

Прежняя форма {"sku": "..."} принимается по-прежнему — заказ из одной
позиции есть частный случай общего вида.

Ответ содержит позиции, код показывается только у выданных:

    {
      "order_id": "ord_...",
      "amount": 2490,
      "refunded": 500,
      "status": "partially_delivered",
      "items": [
        {"position": 1, "sku": "KEY-GTA5", "amount": 1990,
         "status": "delivered", "code": "a-HHW6-4RX2-DX62"},
        {"position": 2, "sku": "KEY-CS2", "amount": 500,
         "status": "refunded", "refunded_at": "..."}
      ]
    }

Отчёт сверки получил раздел money с тождеством и признаком balanced.

3. ВОСПРОИЗВОДИМЫЙ СКРИПТ
------------------------------------------------------------------------------

    docker compose exec app php bin/partial

Прогоняет четыре сценария и проверяет ожидаемое состояние после каждого.
Ненулевой код возврата означает нарушение.

    partial    часть позиций выдана, за остальные возвращены деньги
    repeat     повтор всех шагов ничего не меняет
    crash      обрыв посреди выдачи, заказ доводится восстановителем
    all_fail   ни одна позиция не выдана, возвращено всё

Отдельный сценарий и повторы:

    docker compose exec app php bin/partial --scenario=crash
    docker compose exec app php bin/partial --repeat=5

Ожидаемый вывод:

    ── часть позиций выдана, за остальные возвращены деньги
       1/1  ок   {"статус":"partially_delivered", ...
                  "позиции":{"1":"delivered","2":"refunded","3":"delivered"},
                  "деньги":{"оплачено":448000,"выдано":398000,
                            "возвращено":50000,"в_работе":0,"сходится":true}}

    Проверок: 22, нарушений: 0

Товар для сценариев готовит сам скрипт: KEY-PARTIAL-OK с запасом на складе
и KEY-PARTIAL-OUT, которого нет ни у одного поставщика. Пустой остаток
задаётся отсутствием строк на складе, а не режимом заглушки, — так сценарий
не зависит от настроек поставщика.

4. РУЧНОЙ ПРОГОН: ЧАСТИЧНАЯ ВЫДАЧА
------------------------------------------------------------------------------

Товар, которого нет ни у кого:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "INSERT INTO products (sku, name, type, price_minor, currency)
            VALUES ('KEY-NOSTOCK', 'Без остатка', 'key', 50000, 'RUB')
       ON CONFLICT (sku) DO NOTHING;"

Заказ из трёх позиций:

    ORDER=$(docker compose exec -T app php -r '
      $body = json_encode(["items" => [
        ["sku" => "KEY-GTA5"], ["sku" => "KEY-NOSTOCK"], ["sku" => "KEY-GTA5"]
      ]]);
      $ch = curl_init("http://nginx/api/orders");
      curl_setopt_array($ch, [CURLOPT_POST => true, CURLOPT_POSTFIELDS => $body,
        CURLOPT_HTTPHEADER => ["Content-Type: application/json"],
        CURLOPT_RETURNTRANSFER => true]);
      echo json_decode(curl_exec($ch), true)["order_id"];')

    echo $ORDER

Оплата на полную сумму заказа (1990 + 500 + 1990):

    curl -s -X POST http://localhost:8080/api/webhooks/payment \
      -H 'Content-Type: application/json' \
      -d "{\"event_id\":\"evt_$RANDOM\",\"order_id\":\"$ORDER\",
           \"status\":\"paid\",\"amount\":4480,\"currency\":\"RUB\",
           \"created_at\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}"

Через несколько секунд фоновый исполнитель выдаёт первую и третью позиции.
Вторая уходит в out_of_stock и после исчерпания попыток возвращается.
Состояние:

    curl -s http://localhost:8080/api/orders/$ORDER | python3 -m json.tool

Ожидается: status partially_delivered, refunded 500, у первой и третьей
позиций поле code, у второй — refunded_at и никакого кода.

Позиции в базе:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT position, sku, status, settled_at FROM order_items
        WHERE order_id = '$ORDER' ORDER BY position;"

5. РУЧНОЙ ПРОГОН: ДЕНЬГИ СХОДЯТСЯ
------------------------------------------------------------------------------

Движение денег по одному заказу:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT account, sum(amount_minor) FROM ledger_entries
        WHERE order_id = '$ORDER' GROUP BY account ORDER BY account;"

Ожидается:

    obligation         0     обязательство исполнено полностью
    refund        -50000     возвращено за невыданную позицию
    revenue      -398000     признано выручкой за две выданные
    settlement    448000     принято от платёжной системы

Сумма столбца равна нулю. Тождество: 448000 = 398000 + 50000 + 0.

По всей системе — раздел money отчёта сверки:

    docker compose exec app php bin/reconcile | head -30

Признак balanced обязан быть истинным при любом состоянии системы.
Если он ложен — в журнале появилась проводка, которой не соответствует
ни выдача, ни возврат.

6. РУЧНОЙ ПРОГОН: ПОВТОР ЛЮБОГО ШАГА
------------------------------------------------------------------------------

Повторная доставка платёжного события с тем же event_id. Идентификатор
берётся из базы, а не придумывается: новый id — уже другое событие.

    EVENT=$(docker compose exec -T db psql -U gamer -d gamer_market -tA -c \
      "SELECT event_id FROM payment_events
        WHERE order_id = '$ORDER' AND outcome = 'applied';")

    curl -s -X POST http://localhost:8080/api/webhooks/payment \
      -H 'Content-Type: application/json' \
      -d "{\"event_id\":\"$EVENT\",\"order_id\":\"$ORDER\",
           \"status\":\"paid\",\"amount\":4480,\"currency\":\"RUB\",
           \"created_at\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}"

Ответ duplicate, число строк в журнале не изменилось.

С новым event_id ответ будет ignored: событие принято, но заказ уже
в конечном состоянии, перехода в paid из него нет. Исход другой, итог
тот же — денег второй раз не приняли.

Повторная выдача и повторный возврат по каждой позиции:

    docker compose exec -e ORDER=$ORDER app php -r '
      $c = require "/app/src/bootstrap.php";
      $order = getenv("ORDER");
      foreach ([1, 2, 3] as $p) {
        printf("позиция %d: выдача %s, возврат %s\n", $p,
          ($c->get(App\Services\DeliverOrderItem::class))($order, $p),
          ($c->get(App\Services\RefundItem::class))($order, $p) ? "да" : "нет");
      }' 2>&1

Ожидается noop у выданных и возвращённых позиций и «возврат нет» везде.

Число строк журнала до и после обязано совпасть:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT count(*) FROM ledger_entries WHERE order_id = '$ORDER';"

Восемь строк: две на оплату, по две на каждую выдачу, две на возврат.

7. РУЧНОЙ ПРОГОН: ОБРЫВ ПОСРЕДИ ВЫДАЧИ
------------------------------------------------------------------------------

Сценарий воспроизводится скриптом целиком:

    docker compose exec app php bin/partial --scenario=crash

Вручную: заказ из двух позиций, первая выдана, вторая помечена как взятая
в работу час назад, задачи удалены — состояние, в котором исполнитель
остановился посреди обращения к поставщику.

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT i.position, i.status AS позиция, d.status AS выдача, d.claimed_at
         FROM order_items i
         LEFT JOIN deliveries d ON d.order_id = i.order_id AND d.position = i.position
        WHERE i.order_id = '$ORDER' ORDER BY i.position;"

Доводка:

    docker compose exec app php bin/heal --verbose

Ожидается ненулевое «освобождено позиций» и «отправлено в очередь позиций».
После обработки очереди заказ приходит в конечное состояние: позиция была
занята, но не завершена, повтор идёт к тому же поставщику с тем же
идентификатором запроса и второго кода не создаёт.

8. РУЧНОЙ ПРОГОН: ЗАПРЕТ ВОЗВРАТА ИЗ НЕОПРЕДЕЛЁННОСТИ
------------------------------------------------------------------------------

Поставщик выдаёт код и молчит:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' \
      -d '{"mode":"issue_then_timeout","hang_seconds":3}'

Заказ из одной позиции, оплата, ожидание. Позиция уходит в unresolved:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT position, status FROM order_items WHERE order_id = '$ORDER';"

Попытка вернуть деньги напрямую:

    docker compose exec -e ORDER=$ORDER app php -r '
      $c = require "/app/src/bootstrap.php";
      var_dump(($c->get(App\Services\RefundItem::class))(getenv("ORDER"), 1));'

Ожидается false. Сколько бы попыток ни было исчерпано, из unresolved
возврата нет: код мог быть выдан, и возврат отдал бы покупателю и деньги,
и товар.

Поставщик восстановлен:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"ok"}'

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE jobs SET run_at = now() WHERE status = 'pending';"

Повтор обращается к тому же поставщику с тем же request_id и получает
ранее занятый код. Заказ становится delivered, второго кода на складе
не занято:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT count(*) FROM provider_stock WHERE request_id LIKE '%$ORDER%';"

Ожидается 1.
