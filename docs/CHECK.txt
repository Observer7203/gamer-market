ПРОВЕРКА ЭТАПОВ 1 И 2
Автоматические тесты, проверка конкуренции, ручной прогон сценариев
------------------------------------------------------------------------------

Раздел 1 — автоматические тесты, основной способ проверки.
Раздел 2 — проверка exactly-once под конкуренцией.
Разделы 3-12 — те же сценарии вручную, для наблюдения за поведением системы.

Все команды выполняются из корня проекта. Порт приложения — 8080,
веб-панель базы — 8081. Внутри контейнеров приложение доступно
по адресу http://nginx.

    docker compose exec app composer install

Полная пересборка с чистой базой:

    docker compose down -v && docker compose up -d
    docker compose exec app php bin/migrate && docker compose exec app php bin/seed

1. АВТОМАТИЧЕСКИЕ ТЕСТЫ
------------------------------------------------------------------------------

Основной способ проверки. Разделы ниже описывают ручной прогон тех же
сценариев и нужны для наблюдения за системой, а не для приёмки.

    docker compose exec app vendor/bin/phpunit

    .............................................................  61 / 61 (100%)
    OK (61 tests, 137 assertions)

Прогон занимает около двух секунд: веб-сервер не поднимается, запрос
подаётся прямо в диспетчер.

Выборочный запуск:

    docker compose exec app vendor/bin/phpunit --testsuite unit
    docker compose exec app vendor/bin/phpunit --testsuite feature
    docker compose exec app vendor/bin/phpunit --testsuite concurrency
    docker compose exec app vendor/bin/phpunit tests/Unit/OrderTest.php
    docker compose exec app vendor/bin/phpunit --filter testНесоответствиеСуммы

С названиями сценариев вместо точек:

    docker compose exec app vendor/bin/phpunit --testdox

Остановиться на первом падении:

    docker compose exec app vendor/bin/phpunit --stop-on-failure

Что покрыто
~~~~~~~~~~~

    tests/Unit/          28 тестов, без базы и сети
      OrderTest          8 разрешённых переходов, 7 запрещённых, финальные
                         состояния, сверка суммы и валюты, сортируемость id
      MoneyTest          перевод единиц в обе стороны, обратимость
      RouterTest         параметры пути, учёт метода, границы плейсхолдера

    tests/Concurrency/    3 теста, требуют поднятого окружения
      RaceTest           запускает bin/race в трёх режимах

    tests/Feature/       30 тестов, полный стек через диспетчер
      CreateOrderTest    сумму определяет сервер, цена фиксируется в момент
                         создания, неизвестный и снятый с продажи артикул,
                         чтение заказа
      PaymentWebhookTest applied, duplicate, ignored, amount_mismatch,
                         order_not_found, payment_failed, superseded,
                         7 вариантов нарушения формата
      DeliveryTest       сквозной путь до кода, одна выдача на заказ,
                         код не уходит в два заказа, пустой остаток
                         и восстановление, повтор к поставщику

Отдельная база
~~~~~~~~~~~~~~

Тесты работают с базой gamer_market_test, она создаётся при первом прогоне.
Данные разработки не затрагиваются.

Атрибут force в секции env файла phpunit.xml обязателен: без него значение
не перекрывает переменную, уже установленную в окружении контейнера,
и прогон уходит в рабочую базу.

Заглушка поставщика в тестах вызывается внутри процесса через
Tests\Support\LocalProviderClient. По HTTP запрос ушёл бы в другой процесс
с другим подключением к базе.

Состояние тестовой базы:

    docker compose exec db psql -U gamer -d gamer_market_test -c \
      "SELECT count(*) FROM provider_stock;"

Удалить её целиком (пересоздастся при следующем прогоне):

    docker compose exec db psql -U gamer -d postgres -c \
      "DROP DATABASE gamer_market_test;"

2. ПРОВЕРКА EXACTLY-ONCE ПОД КОНКУРЕНЦИЕЙ
------------------------------------------------------------------------------

    docker compose exec app php bin/race

Скрипт создаёт заказ, обрушивает на него параллельные запросы и проверяет
инварианты. Ненулевой код возврата означает нарушение хотя бы одного.

    docker compose exec app php bin/race --parallel=50 --repeat=20
    docker compose exec app php bin/race --mode=same
    docker compose exec app php bin/race --mode=different
    docker compose exec app php bin/race --mode=workers
    docker compose exec app php bin/race --parallel=100 --repeat=5

Три режима
~~~~~~~~~~

    same        Одно событие доставляется в N копий одновременно.
                Проверяется дедупликация по event_id.
                Ожидается: applied 1, duplicate N-1.

    different   N разных событий по одному заказу одновременно.
                Дедупликация здесь не работает — держат блокировка строки
                заказа и белый список переходов.
                Ожидается: applied 1, ignored N-1.

    workers     N процессов одновременно выполняют выдачу одного заказа.
                Воспроизводит ситуацию, когда задачу подхватил второй
                исполнитель после истечения срока удержания.
                Ожидается: delivered 1, noop N-1.

Как создаётся конкуренция
~~~~~~~~~~~~~~~~~~~~~~~~~

Внутри одного процесса PHP параллельность недостижима, поэтому:

    curl_multi     открывает N соединений сразу, запросы попадают в разные
                   процессы php-fpm (пул статический, 24 процесса)
    pcntl_fork     порождает N процессов для режима workers, каждый
                   с собственным подключением к базе

Проверяемые инварианты
~~~~~~~~~~~~~~~~~~~~~~

После каждого прогона:

    ровно одна выдача на заказ
    выдача завершена
    ровно один код списан со склада
    заказ в состоянии delivered
    ровно одно событие применено
    ни одно событие не потеряно

Пример вывода
~~~~~~~~~~~~~

    ── одинаковый event_id — дедупликация события
       1/5  ок за  111 мс   {"applied":1,"duplicate":49}

    ── разные event_id — блокировка строки заказа
       1/5  ок за  183 мс   {"ignored":49,"applied":1}

    ── конкурирующие исполнители выдачи
       1/5  ок за  168 мс   {"noop":49,"delivered":1}

    Проверок: 90, нарушений: 0

Тот же сценарий как автоматический тест:

    docker compose exec app vendor/bin/phpunit --testsuite concurrency

Набор требует поднятого окружения и работает с основной базой: заглушка
поставщика отвечает из контейнера приложения.

Проверка по всей базе
~~~~~~~~~~~~~~~~~~~~~

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'заказов с двумя выдачами' AS нарушение,
           (SELECT count(*) FROM (SELECT order_id FROM deliveries
              GROUP BY order_id HAVING count(*) > 1) x)::text
    UNION ALL SELECT 'код выдан дважды',
           (SELECT count(*) FROM (SELECT code FROM provider_stock
              WHERE request_id IS NOT NULL GROUP BY code HAVING count(*) > 1) x)::text
    UNION ALL SELECT 'request_id использован дважды',
           (SELECT count(*) FROM (SELECT request_id FROM provider_stock
              WHERE request_id IS NOT NULL GROUP BY request_id HAVING count(*) > 1) x)::text
    UNION ALL SELECT 'два применённых события на заказ',
           (SELECT count(*) FROM (SELECT order_id FROM payment_events
              WHERE outcome = 'applied' GROUP BY order_id HAVING count(*) > 1) x)::text;"

Все четыре значения обязаны быть нулевыми независимо от числа прогонов.

3. СКВОЗНОЙ ПУТЬ: ЗАКАЗ, ОПЛАТА, ВЫДАЧА
------------------------------------------------------------------------------

Создание заказа:

    curl -s -X POST http://localhost:8080/api/orders \
         -H 'Content-Type: application/json' \
         -d '{"sku":"KEY-GTA5"}'

    {
        "order_id": "ord_01M1EW079XJP41BT14ZE3F8WKP",
        "sku": "KEY-GTA5",
        "amount": 1990,
        "currency": "RUB",
        "status": "created"
    }

Сумму присылает сервер, а не клиент: поле amount в запросе игнорируется.

Сохранить идентификатор в переменную:

    ID=$(curl -s -X POST http://localhost:8080/api/orders \
         -H 'Content-Type: application/json' -d '{"sku":"KEY-GTA5"}' \
         | php -r 'echo json_decode(stream_get_contents(STDIN),true)["order_id"];')

Оплата — эмулятор платёжной системы:

    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --url=http://nginx/api/webhooks/payment

    доставок: 1 за 20 мс
      HTTP 200: 1
      исход applied          1

Чтение заказа. Сразу после вебхука статус paid, блока delivery ещё нет;
через доли секунды воркер доводит заказ до delivered:

    curl -s http://localhost:8080/api/orders/$ID

    {
        "order_id": "ord_01M1EW079XJP41BT14ZE3F8WKP",
        "sku": "KEY-GTA5",
        "amount": 1990,
        "currency": "RUB",
        "status": "delivered",
        "delivery": {
            "code": "0K9E-P1FR-BY1U",
            "delivered_at": "..."
        }
    }

Наблюдать переход состояний:

    watch -n 0.3 "curl -s http://localhost:8080/api/orders/$ID | grep status"

4. ПОВТОРНАЯ ДОСТАВКА СОБЫТИЯ
------------------------------------------------------------------------------

Одно и то же событие доставляется дважды. Второй раз ничего не меняет.

    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --event=evt_fixed --url=http://nginx/api/webhooks/payment

    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --event=evt_fixed --url=http://nginx/api/webhooks/payment

Ожидается: первый вызов даёт исход по состоянию заказа, второй — duplicate.

    исход ignored          1
    исход duplicate        1

Новое событие по уже выданному заказу:

    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --url=http://nginx/api/webhooks/payment

    исход ignored          1

Оба случая отвечают 200: ошибка заставила бы платёжную систему
повторять доставку бесконечно.

5. НЕСООТВЕТСТВИЕ СУММЫ
------------------------------------------------------------------------------

    docker compose exec app php bin/pay --order=$ID --amount=500 \
        --url=http://nginx/api/webhooks/payment

    HTTP 200: 1
    исход amount_mismatch  1

Событие принято и помечено; статус заказа не меняется. Ответ успешный:
повторная доставка сумму не исправит, разбирается через сверку.

6. СОБЫТИЕ ПО НЕСУЩЕСТВУЮЩЕМУ ЗАКАЗУ
------------------------------------------------------------------------------

    docker compose exec app php bin/pay --order=ord_NETAKOGO --amount=1990 \
        --url=http://nginx/api/webhooks/payment

    HTTP 200: 1
    исход order_not_found  1

Событие сохранено и ожидает применения:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT event_id, order_id, outcome, processed_at IS NULL AS ждёт
         FROM payment_events WHERE order_id = 'ord_NETAKOGO';"

При появлении заказа с этим идентификатором событие применяется
в той же транзакции, что и его создание.

7. ОШИБКИ ВВОДА
------------------------------------------------------------------------------

Неизвестный артикул:

    curl -s -X POST http://localhost:8080/api/orders \
         -H 'Content-Type: application/json' -d '{"sku":"NO-SUCH-SKU"}'

    404  {"error":{"code":"product_not_found", ...}}

Несуществующий заказ:

    curl -s http://localhost:8080/api/orders/ord_NETAKOGO

    404  {"error":{"code":"order_not_found", ...}}

Сумма строкой вместо числа:

    curl -s -X POST http://localhost:8080/api/webhooks/payment \
         -H 'Content-Type: application/json' \
         -d '{"event_id":"e1","order_id":"o1","status":"paid",
              "amount":"1990","currency":"RUB","created_at":"2025-01-01T12:00:00Z"}'

    400  Поле amount обязательно и должно быть положительным целым числом

Недопустимый статус:

    ... "status":"refunded" ...
    400  Поле status допускает значения paid и failed

Ошибка формата даёт 400. Несоответствие данных заказу даёт 200 и попадает
в сверку — это разные классы проблем.

8. ИСЧЕРПАНИЕ ОСТАТКА И ВОССТАНОВЛЕНИЕ
------------------------------------------------------------------------------

У артикула KEY-EFT на складе четыре кода. Пять оплаченных заказов:

    for i in 1 2 3 4 5; do
      ID=$(curl -s -X POST http://localhost:8080/api/orders \
           -H 'Content-Type: application/json' -d '{"sku":"KEY-EFT"}' \
           | php -r 'echo json_decode(stream_get_contents(STDIN),true)["order_id"];')
      docker compose exec -T app php bin/pay --order=$ID --amount=3490 \
           --url=http://nginx/api/webhooks/payment > /dev/null
    done

Результат через несколько секунд:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT o.id, o.status, coalesce(d.code,'—') AS code
         FROM orders o LEFT JOIN deliveries d ON d.order_id = o.id
        WHERE o.sku = 'KEY-EFT' ORDER BY o.created_at;"

    четыре заказа delivered с разными кодами
    пятый        out_of_stock

Приложение остаётся работоспособным:

    curl -s http://localhost:8080/health        ->  status: ok

Задача возвращена в очередь с отсрочкой:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT status, attempts, last_error, run_at > now() AS отложена
         FROM jobs WHERE status <> 'done' ORDER BY id DESC LIMIT 1;"

    pending | 1 | out_of_stock | t

Отсрочка растёт как 60 x 2^(attempts-1) секунд: 1, 2, 4, 8, 16 минут.
Не дожидаясь, запустить конкретную задачу немедленно:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE jobs SET run_at = now()
        WHERE status = 'pending' AND payload->>'order_id' = '$ID';"

Восстановление — пополнить склад и дождаться повтора (до 60 секунд):

    docker compose exec db psql -U gamer -d gamer_market -c \
      "INSERT INTO provider_stock (provider, sku, code)
       VALUES ('a','KEY-EFT','RSTK-0001-NEW1');"

Пятый заказ доходит до delivered со второй попытки, повторной выдачи
по остальным заказам не происходит.

9. ПРОВЕРКА ИНВАРИАНТОВ
------------------------------------------------------------------------------

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'заказов'        AS метрика, count(*)::text FROM orders
    UNION ALL SELECT 'выдач',           count(*)::text FROM deliveries
    UNION ALL SELECT 'выдач delivered', count(*)::text FROM deliveries WHERE status='delivered'
    UNION ALL SELECT 'кодов выдано',    count(*)::text FROM provider_stock WHERE request_id IS NOT NULL
    UNION ALL SELECT 'кодов дважды',
      (SELECT count(*) FROM (SELECT code FROM provider_stock
        WHERE request_id IS NOT NULL GROUP BY code HAVING count(*) > 1) x)::text;"

Обязательные соотношения:

    кодов дважды     =  0
    выдач            <= заказов
    кодов выдано     >= выдач delivered

Последнее — неравенство, а не равенство: прямые обращения к заглушке
из раздела 9 расходуют коды, не создавая выдач.

Ни один заказ не может иметь двух выдач: ограничение первичного ключа
на deliveries.order_id.

Исходы обработки событий:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT outcome, count(*) FROM payment_events GROUP BY outcome ORDER BY 2 DESC;"

11. ПРЯМОЕ ОБРАЩЕНИЕ К ЗАГЛУШКЕ ПОСТАВЩИКА
------------------------------------------------------------------------------

Заглушка доступна отдельно от основного потока:

    docker compose exec app curl -s -X POST http://nginx/stubs/provider-a/issue \
      -H 'Content-Type: application/json' \
      -d '{"request_id":"req_manual_1","sku":"KEY-GTA5","order_id":"ord_manual"}'

    {"status":"ok","request_id":"req_manual_1","code":"..."}

Повтор с тем же request_id возвращает тот же код:

    (повторить ту же команду — code совпадает)

Запрос по артикулу с пустым остатком:

    409  {"status":"error","reason":"out_of_stock"}

Выданный код закрепляется за request_id навсегда и в выборку свободных
больше не попадает. Прямое обращение расходует склад, не создавая выдачи,
поэтому в разделе 8 соотношение «кодов выдано» и «выдач delivered» —
неравенство.

Освободить коды, израсходованные ручными проверками:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE provider_stock SET request_id = NULL, issued_at = NULL
        WHERE request_id IS NOT NULL
          AND request_id NOT IN
              (SELECT request_id FROM deliveries WHERE request_id IS NOT NULL);"

Остаток по артикулам:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT sku, count(*) FILTER (WHERE request_id IS NULL) AS свободно
         FROM provider_stock GROUP BY sku ORDER BY 2;"
