ПРОВЕРКА ЭТАПА 5
Каталог под нагрузкой
------------------------------------------------------------------------------

Требование: тысячи и более позиций, «горячий» запрос витрины остатков.
Схема и индексы должны сохранять скорость запроса; план выполнения —
объяснён.

Раздел 1 — что сделано.
Раздел 2 — измерения.
Раздел 3 — автоматические тесты.
Разделы 4-6 — ручной прогон.

Все команды выполняются из корня проекта при поднятом окружении.


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Почему витрина — самый нагруженный запрос
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Каталог читают примерно в восемнадцать раз чаще, чем создают заказы
(расчёт в LOAD.txt). Это единственное место, где схема данных влияет
на скорость: остальные запросы выполняются единицы раз на заказ.

Денормализованный остаток
~~~~~~~~~~~~~~~~~~~~~~~~~

Очевидная реализация считает остаток подзапросом по складу поставщиков:

    SELECT p.sku, p.name, p.price_minor,
           (SELECT count(*) FROM provider_stock s
             WHERE s.sku = p.sku AND s.request_id IS NULL) AS available
      FROM products p WHERE p.is_active
     ORDER BY p.sort_rank DESC LIMIT 20

Подзапрос коррелированный: он выполняется для каждой строки-кандидата.
На десятке позиций это незаметно, на пяти тысячах при ста семидесяти тысячах
кодов — 6.9 мс и 6225 прочитанных буферов вместо 21.

Остаток вынесен в колонку products.available_count. Значение поддерживается
триггером на provider_stock: код ушёл в запрос — остаток уменьшился, код
освобождён — вырос. Триггер срабатывает в той же транзакции, что и выдача,
поэтому счётчик не может разойтись с реальным складом.

Покрывающие индексы
~~~~~~~~~~~~~~~~~~~

    CREATE INDEX products_showcase_idx
        ON products (sort_rank DESC, sku DESC)
        INCLUDE (name, type, price_minor, currency, available_count)
        WHERE is_active;

    CREATE INDEX products_showcase_type_idx
        ON products (type, sort_rank DESC, sku DESC)
        INCLUDE (name, price_minor, currency, available_count)
        WHERE is_active;

Ключ повторяет порядок сортировки, поэтому сортировка не требуется вовсе.
Включённые колонки покрывают весь набор выводимых полей, поэтому к самой
таблице обращений не происходит: Heap Fetches равно нулю.

Условие is_active делает индексы частичными. Снятые с продажи позиции в них
не попадают и места не занимают; в сгенерированном каталоге это четверть
тысячи строк из пяти тысяч.

Второй индекс нужен для раздела витрины: без типа в ключе выборка одного
раздела потребовала бы чтения индекса целиком.

Постраничный вывод по ключу
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Смещение заставляет прочитать и отбросить все предыдущие строки: на четырёх
тысячах пропущенных позиций планировщик отказывается от индекса и переходит
к последовательному чтению с сортировкой.

Позиция задаётся парой значений — ранг и артикул:

    WHERE is_active AND (sort_rank, sku) < (?, ?)
    ORDER BY sort_rank DESC, sku DESC LIMIT 20

Пара повторяет ключ индекса, поэтому чтение начинается сразу с нужного места.
Артикул разрешает совпадения рангов: без него строки с одинаковым рангом
могли бы пропускаться или повторяться между страницами.

Курсор возвращается в ответе закодированным, чтобы клиент не собирал его сам.

Наполнение каталога
~~~~~~~~~~~~~~~~~~~

    php bin/seed --scale=5000 --codes-per-sku=20

На десятке позиций планировщик игнорирует любой индекс: последовательное
чтение обходится дешевле, и разница между планами не проявляется. Проверка
имеет смысл только на объёме.

Генератор намеренно оставляет часть позиций снятыми с продажи и часть
без остатка: частичный индекс и отбор по наличию должны проверяться
на реальных данных.

2. ИЗМЕРЕНИЯ
------------------------------------------------------------------------------

    docker compose exec app php bin/explain

Каталог: 5012 позиций, склад: 171705 кодов.

    Запрос                              Время      Буферов   Метод
    ────────────────────────────────────────────────────────────────────────
    остаток подсчётом на лету           6.890 мс      6225   индекс + подзапрос
    остаток из колонки                  0.023 мс        21   только индекс
    раздел витрины по типу              0.150 мс        20   только индекс
    глубокая страница смещением         3.493 мс      2364   последовательное
    глубокая страница по ключу          0.138 мс        21   только индекс

Разница по остатку — в триста раз по времени и в триста по числу
прочитанных буферов. По глубокой странице — в двадцать пять раз.

Полные планы:

    docker compose exec app php bin/explain --full

План оптимизированного запроса:

    Limit (actual time=0.029..0.068 rows=20 loops=1)
      Buffers: shared hit=21
      ->  Index Only Scan using products_showcase_idx on products
            Heap Fetches: 0
            Buffers: shared hit=21
    Execution Time: 0.088 ms

Читается так: Index Only Scan означает, что данные взяты из индекса;
Heap Fetches: 0 — к таблице не обращались ни разу; 21 буфер — прочитан
двадцать один блок по восемь килобайт, то есть 168 КБ вместо 50 МБ.

План наивного запроса:

    Limit (actual time=2.764..8.854 rows=20 loops=1)
      Buffers: shared hit=6331
      ->  Index Only Scan using products_showcase_idx on products
            SubPlan 1
              ->  Aggregate (actual time=0.417..0.417 rows=1 loops=20)
                    ->  Index Only Scan using provider_stock_available_idx
                          Index Cond: (sku = p.sku)

Ключевое здесь — loops=20: подзапрос выполнен двадцать раз, по разу
на каждую выводимую строку. При выводе сотни позиций было бы сто раз.

О числе обращений к таблице
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Сразу после массовой записи Heap Fetches отличается от нуля: карта
видимости ещё не заполнена, и сканирование вынуждено проверять видимость
строк в таблице. После VACUUM обращения исчезают:

    docker compose exec db psql -U gamer -d gamer_market -c "VACUUM ANALYZE products;"

Скрипт измерений выполняет это самостоятельно.

4. РУЧНОЙ ПРОГОН: ВИТРИНА
------------------------------------------------------------------------------

Первая страница:

    curl -s 'http://localhost:8080/api/catalog?limit=3'

    {
        "items": [
            {"sku":"GEN-KEY-00001","name":"Epic Games Deluxe Edition #1",
             "type":"key","price":137,"currency":"RUB","available":40}
        ],
        "next_cursor": "NDk5OTpHRU4tS0VZLTAwMDAx"
    }

Следующая страница по курсору:

    curl -s 'http://localhost:8080/api/catalog?limit=3&after=NDk5OTpHRU4tS0VZLTAwMDAx'

Раздел витрины:

    curl -s 'http://localhost:8080/api/catalog?type=subscription&limit=5'

Только в наличии:

    curl -s 'http://localhost:8080/api/catalog?in_stock=1&limit=5'

Обход каталога целиком:

    CURSOR=""
    TOTAL=0
    while :; do
      PAGE=$(curl -s "http://localhost:8080/api/catalog?limit=100&after=$CURSOR")
      N=$(echo "$PAGE" | php -r '$d=json_decode(stream_get_contents(STDIN),true); echo count($d["items"]);')
      CURSOR=$(echo "$PAGE" | php -r '$d=json_decode(stream_get_contents(STDIN),true); echo $d["next_cursor"] ?? "";')
      TOTAL=$((TOTAL+N))
      [ -z "$CURSOR" ] && break
    done
    echo "обойдено позиций: $TOTAL"

Совпадает с числом активных позиций:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT count(*) FROM products WHERE is_active;"

5. РУЧНОЙ ПРОГОН: ОСТАТОК
------------------------------------------------------------------------------

Счётчик поддерживается триггером, а не приложением: проверяется прямым
изменением склада.

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'до: ' || available_count FROM products WHERE sku='KEY-GTA5';

    UPDATE provider_stock SET request_id='ручная_проверка'
     WHERE sku='KEY-GTA5' AND request_id IS NULL
       AND id = (SELECT min(id) FROM provider_stock
                  WHERE sku='KEY-GTA5' AND request_id IS NULL);

    SELECT 'после выдачи: ' || available_count FROM products WHERE sku='KEY-GTA5';

    UPDATE provider_stock SET request_id=NULL WHERE request_id='ручная_проверка';

    SELECT 'после возврата: ' || available_count FROM products WHERE sku='KEY-GTA5';"

    до: 53
    после выдачи: 52
    после возврата: 53

Сверка счётчика с фактическим складом. Расхождений быть не должно:

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT count(*) AS расхождений FROM (
      SELECT p.sku FROM products p
        LEFT JOIN provider_stock s ON s.sku = p.sku AND s.request_id IS NULL
       GROUP BY p.sku, p.available_count
      HAVING count(s.id) <> p.available_count) x;"

6. НАПОЛНЕНИЕ И СБРОС
------------------------------------------------------------------------------

Каталог на пять тысяч позиций:

    docker compose exec app php bin/seed --scale=5000 --codes-per-sku=20

    сгенерировано позиций: 5000 за 59.2 с
    каталог: 5012 позиций, склад поставщика a: 85928 кодов, поставщика b: 85777

Больший объём:

    docker compose exec app php bin/seed --scale=20000 --codes-per-sku=5

Удаление сгенерированного, исходный каталог остаётся:

    docker compose exec db psql -U gamer -d gamer_market -c "
    DELETE FROM provider_stock WHERE sku LIKE 'GEN-%';
    DELETE FROM products WHERE sku LIKE 'GEN-%';"

Полный сброс:

    docker compose down -v && docker compose up -d
    docker compose exec app php bin/migrate
    docker compose exec app php bin/seed --scale=5000
