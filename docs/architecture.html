Ядро магазина цифровых товаров · техническая документация

Архитектура ядра выдачи

Документ описывает состав компонентов, жизненный цикл заказа и механизмы, обеспечивающие однократную выдачу товара при конкурентной обработке вебхуков, отказах поставщиков и перезапуске процессов.

  • PHP 8.3 без фреймворка
  • PostgreSQL 16
  • очередь в той же БД
  • exactly-once
  • таймаут ≠ отказ

Общая картина

Взаимодействие компонентов

Система состоит из четырёх процессов: веб-процесс (php-fpm), фоновый воркер очереди, планировщик и заглушки поставщиков. Прямых вызовов между ними нет — обмен идёт через таблицы PostgreSQL.

Задача на выдачу создаётся в той же транзакции, что и смена статуса заказа. Оба изменения фиксируются одним COMMIT, поэтому состояние «заказ оплачен, задача отсутствует» недостижимо.

Этап 1 · ядро API

Жизненный цикл заказа

Сквозной сценарий от создания заказа до получения кода клиентом. Сценарий разделён на синхронную и асинхронную части; граница проходит по ответу платёжной системе.

обоснование асинхронной выдачи

Время ответа поставщика достигает 15 секунд при пуле php-fpm в 24 процесса. Синхронный вызов поставщика из обработчика вебхука исчерпывает пул на 25-м запросе и приводит к отказу в обслуживании всех остальных маршрутов, включая витрину.

Этап 2 · exactly-once

Конкурентная обработка вебхуков

Проверочный сценарий — пятьдесят одновременных вебхуков по одному заказу. Проверка факта выдачи перед её выполнением требование не закрывает:

// все 50 процессов выполняют эту строку одновременно
$order = SELECT * FROM orders WHERE id = 'ord_1';

if ($order->code === null) {      // все 50 видят true
    $code = $provider->issue();  // все 50 выдают ключ
}

Условие и запись разделены во времени, поэтому все параллельные обработчики проходят проверку до того, как любой из них завершит выдачу. Проверка на уровне приложения не атомарна. Требование обеспечивается ограничением уникальности, которое делает вторую запись невозможной.

Инварианты уровня БД

UNIQUE (payment_events.event_id)  -- повтор события ничего не меняет
UNIQUE (deliveries.order_id)      -- один факт выдачи на заказ
UNIQUE (stock_pool.order_id)      -- один ключ не уйдёт в два заказа

Инварианты обеспечиваются ограничениями PostgreSQL, а не проверками в приложении, и сохраняются при конкурентном доступе, повторной доставке событий и ошибках в вызывающем коде.

дубли и потери

Ограничения уникальности исключают дубли, но не потери. Если запись «событие обработано» зафиксирована до выполнения выдачи, повторная доставка будет отброшена как дубликат, и выдача не произойдёт. Формально операция идемпотентна, фактически заказ остаётся неисполненным.

Поэтому запись о событии фиксирует не факт получения, а исход обработки: она коммитится вместе с результатом. Заказы, оставшиеся в промежуточном состоянии, обрабатываются фоновой задачей восстановления.

Этап 3 · устойчивые интеграции

Обработка таймаута поставщика

Отсутствие ответа в пределах таймаута не эквивалентно отказу: поставщик мог выполнить выдачу, а ответ — не дойти. Трактовка таймаута как отказа с последующим переключением на резервного поставщика приводит к повторной выдаче по одному заказу.

Условие безопасного повтора

request_id детерминирован и выводится из пары «заказ — поставщик», а не генерируется заново на каждую попытку.

request_id = req_{order_id}_{provider}     // одинаков для всех повторов

// на стороне поставщика:
UNIQUE (provider, request_id) → тот же ключ на тот же запрос

Повтор после таймаута не инициирует новую выдачу, а возвращает результат исходного запроса. Переключение на резервного поставщика допускается только после явного error или out_of_stock, то есть при наличии ответа.

Модель заказа

Состояния заказа

Множество переходов задано белым списком: разрешены только перечисленные, остальные запрещены по умолчанию. Проверка выполняется объектом заказа, владеющим состоянием.

реакция на запрещённый переход

Запрещённый переход обрабатывается как no-op с записью в лог, без исключения. Повторная доставка вебхуков предусмотрена контрактом платёжной системы; ответ 5xx на повтор по уже выданному заказу приводит к бесконечным ретраям.

Проверка надёжности

Проверочные сценарии

Соответствие сценариев отказа и механизмов, которые их закрывают.

№СценарийЧто его закрывает
1 50 параллельных вебхуков — одна выдача SELECT … FOR UPDATE на строке заказа плюс UNIQUE (deliveries.order_id)
2 Повтор с тем же event_id INSERT … ON CONFLICT DO NOTHING: ноль затронутых строк — значит дубль
3 Вебхук вне порядка или раньше заказа Событие сохраняется как «сирота» и применяется при создании заказа
4 Таймаут у поставщика, который выдал код Исход unknown вместо failed, повтор с тем же request_id
5 Поставщик A недоступен, fallback на B Переход на резерв только после явного ответа A, не после его молчания
6 Пустой остаток Статус out_of_stock как рабочее ожидание, healer добивает после пополнения

Наблюдаемость и сверка

Логи структурные: одна строка — один JSON-объект с каналом и сквозными идентификаторами order_id, event_id, request_id. История заказа выбирается одним запросом по идентификатору.

Отчёт сверки формирует две выборки, которые в корректном состоянии системы пусты: «оплачен, но не выдан» и «выдан, но не оплачен». Журнал денежных движений ведётся двойной записью; равенство суммы проводки нулю проверяется отложенным ограничением на уровне БД.
