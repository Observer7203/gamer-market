ПРОВЕРКА ЭТАПА 2
Exactly-once под конкуренцией
------------------------------------------------------------------------------

Требование: дубли и параллельные вебхуки по одному заказу приводят к выдаче
ровно один раз, без потерь.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Раздел 3 — воспроизводимый скрипт проверки.
Разделы 4-6 — ручной прогон.
Раздел 7 — устранённая взаимная блокировка.

Все команды выполняются из корня проекта при поднятом окружении.

После изменения кода выдачи обязателен перезапуск фоновых процессов:

    docker compose restart worker scheduler

Воркер — долгоживущий процесс PHP, он держит загруженный код в памяти.
Работающий рядом со свежими исполнителями старый код даёт расхождение
порядка изменения строк и, как следствие, взаимные блокировки.


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Механизмы
~~~~~~~~~

Дедупликация события. Первичный ключ payment_events.event_id и вставка
через ON CONFLICT DO NOTHING. Ноль затронутых строк означает, что событие
уже принято; обработка не начинается.

Запись события и его применение выполняются одной транзакцией. Раздельный
коммит привёл бы к состоянию, в котором повторная доставка отбрасывается
как дубликат, а заказ остаётся неисполненным — формально идемпотентно,
фактически потеря.

Сериализация по заказу. Применение события начинается с
SELECT ... FROM orders WHERE id = ? FOR UPDATE. Параллельные обработчики
выстраиваются на строке заказа, и только первый застаёт состояние,
допускающее переход.

Белый список переходов. Второй и последующие обработчики видят заказ уже
в состоянии paid: перехода created -> paid из него нет, событие получает
исход ignored. Дедупликация здесь не работает — событий несколько и все
они разные.

Однократность выдачи. Первичный ключ deliveries.order_id: вторую строку
по заказу вставить невозможно. Слот занимается условным обновлением
по статусу выдачи; если затронуто ноль строк, работу уже ведёт другой
исполнитель и второй прекращает работу с исходом noop.

Однократность списания кода. Уникальный индекс
provider_stock (provider, request_id) и захват свободного кода одним
оператором с FOR UPDATE SKIP LOCKED и RETURNING.

Отсутствие очереди ожидания на строке заказа. Захват решается одним
условным оператором, явных блокировок чтением в пути выдачи нет.
Подробности в разделе 7.

Средства проверки
~~~~~~~~~~~~~~~~~

    bin/race                       воспроизводимый скрипт, три режима
    tests/Concurrency/RaceTest     тот же сценарий автоматическим набором
    bin/pay --parallel=N           одиночный залп для ручного наблюдения

Результат
~~~~~~~~~

    50 параллельных x 30 повторов x 3 режима    540 проверок, 0 нарушений
    50 параллельных x 40 повторов, workers x 3  720 проверок, 0 нарушений
    100 параллельных x 10 повторов              180 проверок, 0 нарушений

По всей базе после прогонов:

    заказов                125
    выдач                  125
    кодов выдано           125
    событий               2629
    заказов с 2+ выдачами    0
    кодов выдано дважды      0
    request_id дважды        0

Набор конкуренции:

    docker compose exec app vendor/bin/phpunit --testsuite concurrency

    ✔ ИнвариантыДержатсяПодКонкуренцией with data set "одинаковый event_id"
    ✔ ИнвариантыДержатсяПодКонкуренцией with data set "разные event_id"
    ✔ ИнвариантыДержатсяПодКонкуренцией with data set "конкурирующие исполнители"

    OK (3 tests, 6 assertions)

Весь прогон вместе с этапом 1:

    docker compose exec app vendor/bin/phpunit

    OK (61 tests, 137 assertions)

Последовательные повторы — часть набора feature, отдельного окружения
не требуют:

    docker compose exec app vendor/bin/phpunit --filter testПовторного
    docker compose exec app vendor/bin/phpunit --filter testНовоеСобытие
    docker compose exec app vendor/bin/phpunit --filter testСобытиеСозданное

Набор concurrency требует поднятого окружения и работает с основной базой:
заглушка поставщика отвечает из контейнера приложения, поэтому окружение
задаётся команде явно. При недоступном http://nginx тесты помечаются
пропущенными, а не проваленными.

3. ВОСПРОИЗВОДИМЫЙ СКРИПТ
------------------------------------------------------------------------------

    docker compose exec app php bin/race

Скрипт создаёт заказ, обрушивает на него параллельные запросы, дожидается
конечного состояния и проверяет инварианты. Ненулевой код возврата означает
нарушение хотя бы одного.

Параметры:

    --parallel=N    число одновременных запросов, по умолчанию 50
    --repeat=N      повторов сценария, по умолчанию 10
    --mode=...      same | different | workers | all
    --sku=...       артикул, по умолчанию KEY-GTA5

Примеры:

    docker compose exec app php bin/race --parallel=50 --repeat=20
    docker compose exec app php bin/race --mode=different --parallel=100
    docker compose exec app php bin/race --mode=workers --repeat=30

Три режима
~~~~~~~~~~

    same        Одно событие доставляется в N копий одновременно.
                Проверяет дедупликацию по event_id.
                Ожидается: applied 1, duplicate N-1.

    different   N разных событий по одному заказу одновременно.
                Дедупликация не применима — события разные. Держат
                блокировка строки заказа и белый список переходов.
                Ожидается: applied 1, ignored N-1.

    workers     N процессов одновременно выполняют выдачу одного заказа.
                Воспроизводит ситуацию, когда задачу подхватил второй
                исполнитель после истечения срока удержания.
                Ожидается: delivered 1, noop N-1.

Как создаётся конкуренция
~~~~~~~~~~~~~~~~~~~~~~~~~

Внутри одного процесса PHP параллельность недостижима, поэтому:

    curl_multi    открывает N соединений сразу; запросы попадают в разные
                  процессы php-fpm, пул статический на 24 процесса
    pcntl_fork    порождает N процессов для режима workers, каждый
                  с собственным подключением к базе

Проверяемые инварианты
~~~~~~~~~~~~~~~~~~~~~~

    ровно одна выдача на заказ
    выдача завершена
    ровно один код списан со склада
    заказ в состоянии delivered
    ровно одно событие применено
    ни одно событие не потеряно

Ожидаемый вывод
~~~~~~~~~~~~~~~

    ── одинаковый event_id — дедупликация события
       1/5  ок за  111 мс   {"applied":1,"duplicate":49}

    ── разные event_id — блокировка строки заказа
       1/5  ок за  183 мс   {"ignored":49,"applied":1}

    ── конкурирующие исполнители выдачи
       1/5  ок за  168 мс   {"noop":49,"delivered":1}

    Проверок: 90, нарушений: 0

Код возврата:

    docker compose exec app php bin/race --repeat=5 > /dev/null; echo $?

    0   инварианты соблюдены
    1   зафиксировано нарушение
    2   не удалось создать заказ

4. РУЧНОЙ ПРОГОН: ОДИНАКОВЫЙ EVENT_ID
------------------------------------------------------------------------------

Создание заказа:

    ID=$(curl -s -X POST http://localhost:8080/api/orders \
         -H 'Content-Type: application/json' -d '{"sku":"KEY-GTA5"}' \
         | php -r 'echo json_decode(stream_get_contents(STDIN),true)["order_id"];')

Пятьдесят одновременных доставок одного события. Идентификатор события
уникален глобально, поэтому для каждого прогона он должен быть новым:
повторное использование даст пятьдесят дубликатов и ни одного применения.

    EV=evt_$(date +%s)
    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --event=$EV --parallel=50 \
        --url=http://nginx/api/webhooks/payment

Ожидается:

    доставок: 50 за 106 мс
      HTTP 200: 50
      исход applied          1
      исход duplicate       49

Ни один запрос не должен вернуть 5xx: ошибка заставила бы платёжную
систему повторить доставку.

Состояние после обработки:

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'событий' AS м, count(*)::text FROM payment_events WHERE order_id='$ID'
    UNION ALL SELECT 'выдач', count(*)::text FROM deliveries WHERE order_id='$ID'
    UNION ALL SELECT 'кодов', count(*)::text FROM provider_stock
                              WHERE request_id LIKE '%'||'$ID'||'%'
    UNION ALL SELECT 'статус', status FROM orders WHERE id='$ID';"

    событий | 1
    выдач   | 1
    кодов   | 1
    статус  | delivered

Событие ровно одно: сорок девять доставок отсечены первичным ключом.


==============================================================================
5. РУЧНОЙ ПРОГОН: РАЗНЫЕ EVENT_ID
------------------------------------------------------------------------------

Жёсткий случай. Дедупликация не применима — события разные, все попадают
в базу. Однократность держат блокировка строки заказа и белый список
переходов.

    ID=$(curl -s -X POST http://localhost:8080/api/orders \
         -H 'Content-Type: application/json' -d '{"sku":"KEY-GTA5"}' \
         | php -r 'echo json_decode(stream_get_contents(STDIN),true)["order_id"];')

    docker compose exec app php bin/pay --order=$ID --amount=1990 \
        --parallel=50 --url=http://nginx/api/webhooks/payment

Ожидается:

    доставок: 50 за 172 мс
      HTTP 200: 50
      исход applied          1
      исход ignored         49

Состояние:

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'событий' AS м, count(*)::text FROM payment_events WHERE order_id='$ID'
    UNION ALL SELECT 'applied', count(*)::text FROM payment_events
                                WHERE order_id='$ID' AND outcome='applied'
    UNION ALL SELECT 'ignored', count(*)::text FROM payment_events
                                WHERE order_id='$ID' AND outcome='ignored'
    UNION ALL SELECT 'выдач', count(*)::text FROM deliveries WHERE order_id='$ID'
    UNION ALL SELECT 'кодов', count(*)::text FROM provider_stock
                              WHERE request_id LIKE '%'||'$ID'||'%'
    UNION ALL SELECT 'статус', status FROM orders WHERE id='$ID';"

    событий | 50     все приняты, ни одно не потеряно
    applied | 1      применено ровно одно
    ignored | 49     остальные застали заказ уже оплаченным
    выдач   | 1
    кодов   | 1
    статус  | delivered

Пятьдесят событий в базе против одной выдачи — это и есть требование
«без потерь и дублей»: события сохранены все, эффект однократный.


==============================================================================
6. РУЧНОЙ ПРОГОН: КОНКУРИРУЮЩИЕ ИСПОЛНИТЕЛИ
------------------------------------------------------------------------------

Проверяет вторую половину задачи: одновременную выдачу несколькими
процессами. Воспроизводится только скриптом — команда порождает процессы
через fork.

    docker compose exec app php bin/race --mode=workers --parallel=50 --repeat=10

Ожидается delivered 1 и noop 49 в каждом прогоне.

Дополнительно можно поднять несколько фоновых воркеров:

    docker compose up -d --scale worker=5
    docker compose exec app php bin/race --mode=different --repeat=10
    docker compose up -d --scale worker=1

Число воркеров на результат не влияет: захват задачи выполняется
через FOR UPDATE SKIP LOCKED, одна задача одному исполнителю.


==============================================================================
7. УСТРАНЁННЫЕ ВЗАИМНЫЕ БЛОКИРОВКИ
------------------------------------------------------------------------------

Режим workers выявил два дефекта, невоспроизводимых последовательными
командами. Оба проявлялись как SQLSTATE 40P01.

Первый: расхождение порядка изменения строк
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Транзакции выдачи работали со строками в разном порядке:

    claim()   SELECT orders FOR UPDATE        строка заказа
              INSERT INTO deliveries          строка выдачи

    store()   UPDATE deliveries               строка выдачи
              UPDATE orders                   строка заказа

Один процесс удерживал строку выдачи и ждал строку заказа, другой —
наоборот. Блокировки снимаются только при коммите, коммит не наступает.

Второй: очередь ожидания на одной строке
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Выравнивания порядка оказалось недостаточно. Полусотня исполнителей,
одновременно запросивших SELECT ... FOR UPDATE по одной строке заказа,
образует очередь ожидания. PostgreSQL сериализует её через блокировку
кортежа, и при переупорядочивании очереди, вызванном обновлением строки,
образуется цикл:

    Process A waits for AccessExclusiveLock on tuple  blocked by B
    Process B waits for ShareLock on transaction      blocked by C
    Process C waits for ShareLock on transaction      blocked by D
    Process D waits for ExclusiveLock on tuple        blocked by A

Исправление
~~~~~~~~~~~

Явные блокировки чтением убраны из пути выдачи полностью. Исполнителя
определяет один условный оператор:

    UPDATE deliveries d
       SET status = 'in_flight', attempts = d.attempts + 1,
           provider = ?, request_id = ?
      FROM orders o
     WHERE d.order_id = ? AND o.id = d.order_id
       AND d.status IN ('pending', 'failed', 'out_of_stock')
       AND o.status NOT IN ('delivered', 'payment_failed')
 RETURNING o.sku

Ноль затронутых строк означает, что работу ведёт другой исполнитель либо
заказ в конечном состоянии. Оператор атомарен, очередь ожидания
не образуется, присоединённая таблица заказов читается без блокировки.

Перевод заказа в delivering выполняется условием в самом операторе,
без предварительного чтения:

    UPDATE orders SET status = 'delivering'
     WHERE id = ? AND status IN ('paid', 'out_of_stock', 'delivery_failed')

Обе транзакции изменяют строки в одном порядке: выдача, затем заказ.

Третий фактор: устаревший код в фоновом процессе
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

После исправления блокировки продолжали возникать через раз. Причина
оказалась не в коде: контейнер воркера был запущен до правки и держал
прежнюю версию в памяти. Работая рядом со свежими исполнителями, он
сохранял старый порядок изменения строк и замыкал цикл.

    docker compose restart worker scheduler

Проверка
~~~~~~~~

    docker compose exec app php bin/race --mode=workers --parallel=50 --repeat=40
    docker compose exec app php bin/race --parallel=50 --repeat=30
    docker compose exec app php bin/race --parallel=100 --repeat=10

Суммарно 1440 проверок без единого нарушения и без прерванных транзакций.
До исправления прогон завершался фатальной ошибкой.

8. ПРОВЕРКА ПО ВСЕЙ БАЗЕ
------------------------------------------------------------------------------

Не зависит от числа прогонов: все четыре значения обязаны быть нулевыми.

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'заказов с двумя выдачами' AS нарушение,
           (SELECT count(*) FROM (SELECT order_id FROM deliveries
              GROUP BY order_id HAVING count(*) > 1) x)::text AS значение
    UNION ALL SELECT 'код выдан дважды',
           (SELECT count(*) FROM (SELECT code FROM provider_stock
              WHERE request_id IS NOT NULL GROUP BY code HAVING count(*) > 1) x)::text
    UNION ALL SELECT 'request_id использован дважды',
           (SELECT count(*) FROM (SELECT request_id FROM provider_stock
              WHERE request_id IS NOT NULL GROUP BY request_id HAVING count(*) > 1) x)::text
    UNION ALL SELECT 'два применённых события на заказ',
           (SELECT count(*) FROM (SELECT order_id FROM payment_events
              WHERE outcome = 'applied' GROUP BY order_id HAVING count(*) > 1) x)::text;"

Сводка объёмов:

    docker compose exec db psql -U gamer -d gamer_market -c "
    SELECT 'заказов' AS м, count(*)::text FROM orders
    UNION ALL SELECT 'выдач', count(*)::text FROM deliveries
    UNION ALL SELECT 'кодов выдано', count(*)::text FROM provider_stock
                                     WHERE request_id IS NOT NULL
    UNION ALL SELECT 'событий', count(*)::text FROM payment_events;"

Соотношение «выдач» и «кодов выдано» совпадает, если склад не расходовался
прямыми обращениями к заглушке.

Распределение исходов:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT outcome, count(*) FROM payment_events GROUP BY outcome ORDER BY 2 DESC;"
