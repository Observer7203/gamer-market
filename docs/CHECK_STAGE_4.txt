ПРОВЕРКА ЭТАПА 4
Наблюдаемость, сверка, восстановление, журнал денежных движений
------------------------------------------------------------------------------

Требование: структурированные логи по платежам и выдаче; отчёт сверки
«оплачен, но не выдан» и «выдан, но не оплачен»; фоновая задача, безопасно
доводящая зависшие заказы; журнал денежных движений, который всегда сходится.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Разделы 3-7 — ручной прогон.

Все команды выполняются из корня проекта при поднятом окружении.


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Журнал денежных движений
~~~~~~~~~~~~~~~~~~~~~~~~

Двойная запись: каждая проводка состоит из строк, сумма которых равна нулю.
Деньги не возникают и не исчезают, а перемещаются между счетами.

    settlement    средства, поступившие от платёжной системы
    obligation    обязательство выдать оплаченный товар
    revenue       признанная выручка

Поступление оплаты:

    settlement  +1990.00
    obligation  -1990.00

Выдача товара:

    obligation  +1990.00
    revenue     -1990.00

Баланс obligation равен сумме оплаченных, но не выданных заказов. Это
не отдельный счётчик, а следствие двойной записи: журнал сам показывает
размер неисполненного обязательства.

Баланс счёта не хранится колонкой, а вычисляется суммой движений. Хранимое
значение было бы вторым источником правды и могло разойтись с журналом,
а сверять его стало бы не с чем.

Проводки записываются в той же транзакции, что и изменение состояния заказа:
состояния «оплачен, но в журнале пусто» не существует.

Идентификатор проводки выводится из события платёжной системы либо из заказа,
поэтому повторная запись того же факта невозможна — за этим следит
уникальный индекс на паре (txn_id, account).

Проверка баланса на уровне базы
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Ограничение CHECK охватывает одну строку и для проверки суммы непригодно.
Используется отложенный триггер: он проверяет сумму проводки в момент
фиксации транзакции, когда все строки уже вставлены.

    CREATE CONSTRAINT TRIGGER ledger_entries_balanced
        AFTER INSERT OR UPDATE OR DELETE ON ledger_entries
        DEFERRABLE INITIALLY DEFERRED
        FOR EACH ROW EXECUTE FUNCTION ledger_txn_balanced();

Несбалансированная проводка не фиксируется независимо от того, какой код
пытается её записать.

Отчёт сверки
~~~~~~~~~~~~

    оплачен, но не выдан           деньги получены, товар не отдан
    выдан, но не оплачен           товар отдан без подтверждённой оплаты
    зависшие задачи                взяты в работу и не завершены
    выдачи без ответа поставщика   состояние поставщика неизвестно
    непринятые события             событие по ещё не существующему заказу
    несведённые проводки           сумма проводки отлична от нуля

В исправной системе все шесть разделов пусты. Отчёт доступен эндпоинтом
и командой; код ответа и код возврата отражают результат, поэтому
расхождение видно системе мониторинга без разбора тела.

Фоновая доводка
~~~~~~~~~~~~~~~

Три действия, все идемпотентные:

    возврат брошенных задач    исполнитель остановлен посреди обработки:
                               задача осталась взятой и повторно не будет
                               выбрана без вмешательства

    применение событий         событие пришло раньше заказа и осталось
                               необработанным; при появлении заказа
                               применяется

    возврат заказов в очередь  заказ оплачен, задача утрачена либо исчерпала
                               попытки

Безопасность обеспечивается не осторожностью действий, а их природой.
Повторное обращение к поставщику идёт с прежним идентификатором запроса,
выдачу защищает первичный ключ на заказе, проводку — уникальный индекс.
Повторный запуск ничего не удваивает.

Планировщик запускает доводку раз в минуту.

Структурированные логи
~~~~~~~~~~~~~~~~~~~~~~

Одна строка — один объект JSON. Каждая запись содержит канал и сквозные
идентификаторы, поэтому история заказа собирается одной командой.

    channel: order      создание заказа
    channel: payment    приём и применение событий
    channel: delivery   обращения к поставщику и выдача
    channel: queue      очередь и доводка

Результат
~~~~~~~~~

    журнал сходится при любом числе заказов и сбоев

3. ОТЧЁТ СВЕРКИ
------------------------------------------------------------------------------

Командой:

    docker compose exec app php bin/reconcile

    Сверка на 2026-09-06T10:35:03+00:00

      заказов всего                    4
      выдано                           4
      оплачен, но не выдан             0
      выдан, но не оплачен             0
      зависших задач                   0
      выдач без ответа поставщика      0
      непринятых событий               0
      несведённых проводок             0

    Баланс журнала, минорные единицы:
      obligation                       +0
      revenue                          -796000
      settlement                       +796000
      сумма всех счетов                +0

    Расхождений нет.

Код возврата: 0 при отсутствии расхождений, 1 при их наличии. Пригодно
для планировщика и оповещений:

    docker compose exec app php bin/reconcile > /dev/null || echo "есть расхождения"

Полный отчёт машиночитаемо:

    docker compose exec app php bin/reconcile --json

Эндпоинтом:

    curl -s http://localhost:8080/api/admin/reconciliation

Код ответа 200 при отсутствии расхождений, 409 при их наличии.

4. РУЧНОЙ ПРОГОН: ОПЛАЧЕН, НО НЕ ВЫДАН
------------------------------------------------------------------------------

Оба поставщика недоступны, заказ оплачен:

    mode a error
    mode b error
    ID=$(order); pay $ID; sleep 3

Сверка учитывает время ожидания, поэтому заказ считается зависшим не сразу.
Для проверки давность задаётся вручную:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE orders SET paid_at = now() - interval '10 minutes' WHERE id='$ID';"

    docker compose exec app php bin/reconcile

    оплачен, но не выдан             1

    ОПЛАЧЕН, НО НЕ ВЫДАН
      {"order_id":"ord_...","status":"delivery_failed","price_minor":199000,
       "delivery_status":"failed","last_error":"provider_unavailable",
       "waiting_seconds":600}

Баланс журнала показывает то же самое числом:

      obligation                       -199000

Минус в обязательствах равен сумме, полученной за невыданный товар.
Отчёт и журнал сходятся между собой без дополнительных проверок.

Восстановление:

    mode b ok
    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE jobs SET run_at=now() WHERE status='pending';"
    sleep 5
    docker compose exec app php bin/reconcile

      обязательство обнуляется, расхождений нет

5. РУЧНОЙ ПРОГОН: ФОНОВАЯ ДОВОДКА
------------------------------------------------------------------------------

Планировщик запускает доводку раз в минуту, поэтому для наблюдения его
удобно остановить:

    docker compose stop scheduler worker

Брошенная задача
~~~~~~~~~~~~~~~~

    ID=$(order); pay $ID
    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE jobs SET status='running', locked_at=now() - interval '10 minutes'
        WHERE payload->>'order_id'='$ID';"

    docker compose exec app php bin/heal

    возвращено задач: 1, применено событий: 0, отправлено в очередь заказов: 0

Потерянная задача
~~~~~~~~~~~~~~~~~

    ID=$(order); pay $ID
    docker compose exec db psql -U gamer -d gamer_market -c \
      "DELETE FROM jobs WHERE payload->>'order_id'='$ID';
       UPDATE orders SET paid_at = now() - interval '10 minutes' WHERE id='$ID';"

    docker compose exec app php bin/heal

    возвращено задач: 0, применено событий: 0, отправлено в очередь заказов: 1

Событие раньше заказа
~~~~~~~~~~~~~~~~~~~~~

    FUT=ord_01FUTURE00000000000000000
    docker compose exec app php bin/pay --order=$FUT --amount=1990 \
        --url=http://nginx/api/webhooks/payment

    исход order_not_found

    docker compose exec db psql -U gamer -d gamer_market -c \
      "INSERT INTO orders (id, sku, price_minor, currency, status)
       VALUES ('$FUT','KEY-GTA5',199000,'RUB','created');"

    docker compose exec app php bin/heal

    возвращено задач: 0, применено событий: 1, отправлено в очередь заказов: 0

Заказ переходит в оплаченный: событие не потерялось.

Идемпотентность
~~~~~~~~~~~~~~~

    docker compose exec app php bin/heal
    docker compose exec app php bin/heal

    возвращено задач: 0, применено событий: 0, отправлено в очередь заказов: 0

Вернуть фоновые процессы:

    docker compose start scheduler worker

6. ЖУРНАЛ ДЕНЕЖНЫХ ДВИЖЕНИЙ
------------------------------------------------------------------------------

Баланс по счетам:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT account, sum(amount_minor) AS баланс, count(*) AS строк
         FROM ledger_entries GROUP BY account ORDER BY account;"

      account   | баланс  | строк
    ------------+---------+-------
     obligation |       0 |     6
     revenue    | -597000 |     3
     settlement |  597000 |     3

Главный инвариант:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT sum(amount_minor) AS сумма_всех_счетов FROM ledger_entries;"

    0

Обязан быть нулевым всегда: сумма всех движений по всем счетам.

Проводки одного заказа:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT txn_id, account, amount_minor, reason FROM ledger_entries
        WHERE order_id='$ID' ORDER BY id;"

     pay_evt_...     | settlement |  199000 | payment_received
     pay_evt_...     | obligation | -199000 | payment_received
     deliver_ord_... | obligation |  199000 | order_delivered
     deliver_ord_... | revenue    | -199000 | order_delivered

Две проводки по две строки. Сумма каждой равна нулю.

Проверка отложенного триггера
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Попытка записать одностороннюю проводку:

    docker compose exec db psql -U gamer -d gamer_market -c "
    BEGIN;
    INSERT INTO ledger_entries (txn_id, order_id, account, amount_minor, currency, reason)
    VALUES ('broken', (SELECT id FROM orders LIMIT 1), 'settlement', 100000, 'RUB', 'test');
    COMMIT;"

    ERROR:  Проводка broken не сходится: расхождение 100000 минорных единиц

Сбалансированная проходит:

    docker compose exec db psql -U gamer -d gamer_market -c "
    BEGIN;
    INSERT INTO ledger_entries (txn_id, order_id, account, amount_minor, currency, reason)
    VALUES ('ok_txn', (SELECT id FROM orders LIMIT 1), 'settlement',  100000, 'RUB', 'test'),
           ('ok_txn', (SELECT id FROM orders LIMIT 1), 'obligation', -100000, 'RUB', 'test');
    COMMIT;"

    INSERT 0 2

Проверка выполняется в момент фиксации, а не построчно: между вставками
проводка временно не сходится, и это допустимо.

7. ЛОГИ
------------------------------------------------------------------------------

Одна строка — один объект JSON:

    docker compose exec app tail -5 storage/logs/app.log

История конкретного заказа:

    docker compose exec app grep $ID storage/logs/app.log

    {"event":"order_created",          "channel":"order",    "order_id":"ord_..."}
    {"event":"payment_event_applied",  "channel":"payment",  "outcome":"applied"}
    {"event":"provider_request",       "channel":"delivery", "outcome":"ok","latency_ms":28}
    {"event":"order_delivered",        "channel":"delivery", "provider":"a"}

По каналу:

    docker compose exec app grep '"channel":"payment"' storage/logs/app.log | tail -10
    docker compose exec app grep '"channel":"delivery"' storage/logs/app.log | tail -10

Неудачные обращения к поставщику:

    docker compose exec app grep '"outcome":"unknown"' storage/logs/app.log | tail -10

Журнал воркера:

    docker compose logs worker --tail=30
    docker compose logs scheduler --tail=30
