СХЕМА ДАННЫХ
Принятые решения и инварианты
------------------------------------------------------------------------------

Документ объясняет, почему схема устроена именно так, и какой тест ловит
нарушение каждого решения.


==============================================================================
1. ШЕСТЬ РЕШЕНИЙ
------------------------------------------------------------------------------

1.1 Деньги целым числом в минорных единицах
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    price_minor  bigint NOT NULL CHECK (price_minor > 0)
    amount_minor bigint NOT NULL

Двоичная дробь не выражает 0.1 точно:

    0.1 + 0.2 == 0.3    ->  false, получается 0.30000000000000004

Сравнение сумм, сложение проводок и сверка разъезжаются на третьем знаке.
Целое складывается и сравнивается точно.

Мажорные единицы существуют только на границах: контракт платёжной системы
и ответ API оперируют целыми рублями. Преобразование сосредоточено
в App\Support\Money и выполняется в трёх местах — загрузка каталога,
приём вебхука, формирование ответа.

Тип bigint, а не integer: int вмещает 2 147 483 647 копеек, то есть 21.4 млн
рублей. Отдельной цены это не касается, но накопительные величины журнала
проводок предел превышают. Единый тип по всем денежным колонкам избавляет
от приведений при сравнении и суммировании.

    Проверяется: MoneyTest, CreateOrderTest::testСуммуОпределяетСервер


1.2 Цена копируется в заказ, а не берётся ссылкой
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    orders.price_minor  bigint NOT NULL CHECK (price_minor > 0)
    orders.currency     text   NOT NULL

Заказ хранит сумму на момент создания. Переоценка товара не меняет сумму
уже оформленного заказа: иначе сверка платежей разъедется при первой же
смене цены, а покупатель увидит одну сумму при оформлении и другую в истории.

Ограничение положительной цены продублировано на orders: копирование
выполняет код, и ошибка в нём не должна пройти молча.

    Проверяется: CreateOrderTest::testЦенаФиксируетсяВМоментСоздания


1.3 Инварианты обеспечивают уникальные индексы, а не проверки в коде
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Три ограничения несут инварианты системы:

    payment_events.event_id  PRIMARY KEY
        Повторная доставка события не создаёт второй записи.

    deliveries.order_id  PRIMARY KEY
        На заказ приходится ровно одна выдача.

    provider_stock (provider, request_id)  UNIQUE WHERE request_id IS NOT NULL
        Повтор запроса к поставщику возвращает тот же код, а не новый.

Проверка в коде между чтением и записью не атомарна:

    $order = SELECT ... ;              // все конкурентные процессы читают
    if ($order->code === null) {       // все видят одно и то же
        $provider->issue();            // все выдают
    }

Ограничение движка базы конкурентности не подвержено. Нарушение уникальности
здесь — штатный результат, означающий, что запись уже создана другим
процессом, а не сбой.

    Проверяется: DeliveryTest::testНаЗаказПриходитсяРовноОднаВыдача,
                 DeliveryTest::testКодНеУходитВДваЗаказа,
                 DeliveryTest::testПовторКПоставщикуВозвращаетТотЖеКод,
                 PaymentWebhookTest::testПовторногоСобытияНедостаточно


1.4 Хранятся события, а не только их результат
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    payment_events (event_id, order_id, status, amount_minor, currency,
                    occurred_at, received_at, processed_at, outcome)

Таблица хранит каждое пришедшее событие с исходом обработки: applied,
duplicate, ignored, amount_mismatch, order_not_found, superseded.

Без этого сверка невозможна: по одному лишь статусу заказа нельзя ответить,
почему он не оплачен — событие не приходило, пришло с другой суммой
или было отброшено как устаревшее.

Разделение времён существенно:

    occurred_at   момент события у платёжной системы, задаёт порядок
    received_at   момент доставки к нам
    processed_at  момент применения; NULL означает ожидание

Порядок доставки с порядком возникновения не связан. Событие, созданное
раньше уже применённого, помечается superseded и статус не меняет.

    Проверяется: PaymentWebhookTest::testСобытиеСозданноеРаньшеНеОтменяет...,
                 PaymentWebhookTest::testСобытиеПоНесуществующемуЗаказу...


1.5 Выдача — отдельная сущность, а не колонка в заказе
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    deliveries (order_id, status, provider, request_id, code,
                attempts, last_error, delivered_at)

У выдачи собственное состояние, которое в колонку code не помещается:

    status       pending -> in_flight -> delivered | failed | out_of_stock
    provider     к кому обращались — определяет, куда идти при повторе
    request_id   ключ идемпотентности запроса
    attempts     число попыток
    last_error   причина неудачи

Отдельная таблица нужна и для обработки таймаута: неответ поставщика
не равен отказу, и это третье состояние требует места для хранения.

    Проверяется: DeliveryTest::testСостоянияВыдачиИЗаказаСогласованы


1.6 Внешние ключи и осмысленное их отсутствие
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Связи, которые есть:

    orders.sku          -> products.sku    заказ на несуществующий товар невозможен
    deliveries.order_id -> orders.id       выдача без заказа невозможна

Связи, которых нет намеренно:

    jobs.payload->>'order_id'
        Очередь — инфраструктура. Внешний ключ на orders запретил бы класть
        в неё задачи, не связанные с заказами.

    payment_events.order_id
        Событие может прийти по заказу, которого ещё нет. Внешний ключ
        отверг бы такое событие, что означало бы потерю оплаты.

    provider_stock.sku
        Склад принадлежит поставщику. Его ассортимент может не совпадать
        с нашим каталогом; жёсткая связь смешала бы свои данные с чужими.


==============================================================================
2. ТАБЛИЦЫ
------------------------------------------------------------------------------

products
    Каталог. sku — естественный первичный ключ: он же фигурирует в контракте
    поставщика, поэтому вводить суррогатный идентификатор незачем.

orders
    Заказ. id вида ord_<ULID>: лексикографически сортируемый и монотонный
    по времени, вставки не рандомизируют порядок в btree-индексе,
    в отличие от UUIDv4. По идентификатору не угадывается общее число заказов.

payment_events
    События платёжной системы с исходом обработки.

deliveries
    Факт выдачи. Одна строка на заказ.

jobs
    Очередь фоновых задач. Расположена в той же базе, поэтому задача
    создаётся одной транзакцией с изменением данных: состояние
    «оплачен, но задачи нет» недостижимо.

provider_stock
    Склад заглушки поставщика: одна строка — один код. Принадлежит
    поставщику, а не магазину: по контракту код выдаёт он.

3. ИНДЕКСЫ
------------------------------------------------------------------------------

Частичные индексы покрывают только те строки, которые действительно
выбираются:

    jobs_pending_idx        (run_at) WHERE status = 'pending'
        Воркер выбирает невзятые задачи. Выполненные, которых со временем
        становится большинство, в индекс не попадают.

    jobs_running_idx        (locked_at) WHERE status = 'running'
        Поиск задач, у которых истёк срок удержания.

    payment_events_unapplied_idx  (order_id) WHERE processed_at IS NULL
        События, ожидающие появления заказа. В нормальной работе таких
        строк единицы против миллионов обработанных.

    provider_stock_available_idx  (provider, sku) WHERE request_id IS NULL
        Поиск свободного кода нужного артикула.

    provider_stock_request_idx    (provider, request_id)
                                  UNIQUE WHERE request_id IS NOT NULL
        Идемпотентность запроса к поставщику.

Два последних не пересекаются: один индексирует выданные коды, другой —
свободные. Вместе они покрывают таблицу один раз, а не два.

    orders_status_created_at_idx  (status, created_at)
        Выборка заказов в незавершённых состояниях для сверки
        и восстановления.

4. ЖИЗНЕННЫЙ ЦИКЛ ЗАКАЗА
------------------------------------------------------------------------------

Основной путь:

    created -> paid -> delivering -> delivered

Ветки:

    created    -> payment_failed                             финальная
    delivering -> out_of_stock    -> delivering -> delivered  восстановимая
    delivering -> delivery_failed -> delivering -> delivered  восстановимая

Финальных состояний два: delivered и payment_failed. Тупиковых нет.
out_of_stock и delivery_failed — рабочие состояния ожидания: после пополнения
остатка или восстановления поставщика фоновая задача доводит заказ до выдачи.

Переходы заданы белым списком в App\Models\Order: разрешено только
перечисленное. Проверка принадлежит объекту, а не вызывающему коду.

Запрещённый переход обрабатывается как отсутствие действия с записью в лог,
а не как исключение: повторная доставка вебхуков предусмотрена контрактом,
и ответ 5xx на повтор по уже выданному заказу привёл бы к бесконечным
попыткам доставки.

    Проверяется: OrderTest — 8 разрешённых переходов, 7 запрещённых

5. ЧТО СХЕМА ЗАПРЕЩАЕТ ФИЗИЧЕСКИ
------------------------------------------------------------------------------

Перечисленное невозможно независимо от ошибок в коде и конкурентности:

    две выдачи по одному заказу         deliveries.order_id PRIMARY KEY
    один код в двух заказах             provider_stock (provider, request_id)
    два разных кода на один запрос       то же ограничение
    повторная запись события             payment_events.event_id PRIMARY KEY
    заказ на несуществующий товар        внешний ключ orders.sku
    выдача без заказа                    внешний ключ deliveries.order_id
    товар или заказ с нулевой ценой      CHECK (price_minor > 0)
    один код дважды на складе            UNIQUE (provider, code)
