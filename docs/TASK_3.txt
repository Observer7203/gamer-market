ЗАДАЧА 3
Всплеск заказов и лимит поставщика
------------------------------------------------------------------------------

Требование: поставщик принимает ограниченное число запросов в минуту, а заказов
приходит в разы больше. Нельзя ни терять заказы, ни превышать лимит. При этом
оплаченные обслуживаются раньше неоплаченных, а прогресс должен быть виден.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Раздел 3 — воспроизводимый скрипт.
Разделы 4-7 — ручной прогон.

Все команды выполняются из корня проекта при поднятом окружении.
После изменения кода выдачи обязателен перезапуск фоновых процессов:

    docker compose restart worker scheduler

1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Скользящее окно вместо счётчика
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    CREATE TABLE provider_rate_limits (
        provider text PRIMARY KEY,
        limit_per_minute integer,
        window_seconds integer DEFAULT 60
    );

    CREATE TABLE provider_calls (
        id bigint, provider text, called_at timestamptz
    );

Лимит общий для всех исполнителей, поэтому счётчик не может жить в памяти
процесса: десять воркеров с локальным счётчиком дадут десятикратное
превышение. Состояние лежит в базе.

Окно скользящее, а не календарная минута. Токенное ведро с запасом, равным
лимиту, допускает всплеск: лимит за минуту с 0-й по 60-ю секунду соблюдён,
с 59-й по 119-ю — превышен вдвое. Скользящее окно отвечает на вопрос «сколько
обращений было за последние шестьдесят секунд» и превысить лимит не даёт
ни в какой момент.

Журнал обращений вместо счётчика нужен ещё и для проверки: по счётчику нельзя
узнать, превышался ли лимит в прошлом, — он показывает текущее значение.
Журнал отвечает на вопрос «сколько было обращений в любую минуту прошлого»,
и именно этот вопрос задаёт проверка.

Алгоритм известен как sliding window log. Обычно его делают на Redis:
сортированное множество, где член — метка времени, на каждом обращении
удаляют всё старше окна, считают остаток и добавляют новое. Здесь то же самое
в PostgreSQL, по той же причине, по которой в базе лежит и очередь: не заводить
вторую инфраструктуру ради одной таблицы. Атомарность в Redis обеспечивают
Lua-скриптом, здесь — блокировкой строки лимита.

Занятие места:

    BEGIN
      SELECT ... FROM provider_rate_limits WHERE provider = ? FOR UPDATE
      SELECT count(*) FROM provider_calls
       WHERE provider = ? AND called_at > now() - window
      INSERT INTO provider_calls ...   -- если место есть
    COMMIT

Блокировка строки лимита сериализует претендентов: два исполнителя не могут
одновременно увидеть свободное место и оба его занять. Транзакция своя
и короткая — блокировка не удерживается на время обращения к поставщику.

Место занимается перед каждым обращением, включая повторы и запрос состояния:
это такие же запросы к поставщику, и лимит их не различает.


Отложенная работа вместо проваленной
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Исход выдачи throttled означает «места сейчас нет». Это не отказ и не ошибка:

    - обращения не было, поэтому позиция возвращается в прежнее состояние,
      а счётчик её попыток уменьшается обратно;
    - задача откладывается через Queue::defer, а не Queue::retry: попытка
      не засчитывается.

Разница существенная. Считай система отложенную работу попыткой, всплеск
исчерпал бы бюджет из восьми попыток за полминуты, и задачи, с которыми
ничего не случилось, оказались бы проваленными, а позиции ушли бы в возврат
денег. Ничего не теряется именно поэтому.

Возврат позиции в прежнее состояние опирается на то, что захват вернул её
предыдущий статус: строка order_items в этом операторе не менялась, поэтому
RETURNING отдал значение до захвата.


Приоритет оплаченных
~~~~~~~~~~~~~~~~~~~~

    ALTER TABLE jobs ADD COLUMN priority integer NOT NULL DEFAULT 0;
    CREATE INDEX jobs_pending_idx ON jobs (priority DESC, run_at)
        WHERE status = 'pending';

    ORDER BY priority DESC, run_at, id

Пока очередь короче пропускной способности, порядок безразличен. Под всплеском
он определяет, кто ждёт: оплаченный заказ — обязательство перед покупателем,
оно обслуживается раньше фоновой работы.

    100  оплаченная выдача
     10  работа по заказу без подтверждённой оплаты
      0  фоновая работа

Приоритет — метка класса, а не счётчик: значений всего три, и они не растут
с числом задач. Растёт число строк в jobs, но выборку это не замедляет —
индекс частичный и хранит только ожидающие задачи, а выполненные старше суток
удаляет восстановитель.

Отдельно стоит сказать, что в этой системе неоплаченный заказ вообще
не потребляет квоту поставщика: задача выдачи создаётся той же транзакцией,
что и перевод заказа в оплаченный, а захват позиции требует оплаченного
заказа. Приоритет — вторая линия: если задача по неоплаченному заказу
всё же окажется в очереди, она пропустит вперёд все оплаченные.


Прогресс
~~~~~~~~

    GET /api/admin/queue

    {
      "queue":      {"pending": 24, "deferred": 0, "running": 2,
                     "failed": 0, "paid_ahead": 24},
      "items":      {"awaiting": 24, "unpaid": 8, "delivered": 26,
                     "refunded": 0, "unresolved": 0},
      "providers":  {"a": {"limit_per_minute": 15, "used": 15, "available": 0},
                     "b": {"limit_per_minute": 15, "used": 15, "available": 0}},
      "throughput": {"limit_per_minute": 30, "delivered_last_minute": 30,
                     "waiting": 24, "eta_seconds": 48}
    }

Оценка времени считается из лимита поставщиков, а не из наблюдаемой скорости:
скорость — следствие лимита, и при пустой очереди её просто нет. Это оценка
сверху.

То же самое в терминале:

    docker compose exec app php bin/queue
    docker compose exec app php bin/queue --watch

3. ВОСПРОИЗВОДИМЫЙ СКРИПТ
------------------------------------------------------------------------------

    docker compose exec app php bin/surge

Создаёт заказы, половину оплачивает, запускает несколько исполнителей
в отдельных процессах и печатает прогресс, пока они работают. По окончании
проверяет итог. Ненулевой код возврата означает нарушение.

Параметры и значения по умолчанию:

    --orders=80     сколько заказов создать (половина будет оплачена)
    --limit=10      лимит каждого поставщика, запросов в минуту
    --workers=8     сколько исполнителей запустить
    --seconds=75    сколько наблюдать

Умолчания подобраны так, чтобы всплеск действительно случился: сорок
оплаченных заказов против двадцати запросов в минуту. При избыточной
пропускной способности очередь расходится мгновенно и проверять нечего —
это стоит помнить, задавая свои значения.

Исполнители запускаются отдельными процессами намеренно: лимит общий, и
проверять его имеет смысл только тогда, когда за место претендуют независимые
процессы. Счётчик в памяти одного процесса не доказал бы ничего.

Ожидаемый вывод:

    создано: 40 оплаченных, 40 неоплаченных

      0.0 с  в очереди  80 (оплаченных  40)  выдано  0 из 40  лимит a  0/10 b  0/10  осталось ~240 с
      2.0 с  в очереди  20 (оплаченных  20)  выдано 20 из 40  лимит a 10/10 b 10/10  осталось ~60 с
     ...
     62.5 с  в очереди   0 (оплаченных   0)  выдано 40 из 40  лимит a 10/10 b  0/10  осталось ~0 с

      оплаченных завершено: 40 из 40
      неоплаченных выдано: 0 из 40
      пик обращений в окне: {"a":10,"b":10}
      лимит: 10
      позиций потеряно: 0
      проваленных задач: 0

      ок       лимит поставщика не превышен ни в одном окне
      ок       ни одна позиция не потеряна
      ок       задачи не помечены проваленными
      ок       оплаченные обслужены
      ок       оплаченные обслужены раньше неоплаченных

    Проверок: 5, нарушений: 0

Видно главное: первые двадцать заказов уходят сразу, дальше очередь стоит
ровно столько, сколько нужно окну, чтобы освободить место. Пик обращений
равен лимиту и ни разу его не превышает.

Скрипт меняет лимит на время прогона и возвращает значение окружения
в конце. Остальные сценарные скрипты (race, failover, partial, dishonest)
лимит себе снимают: ограничение частоты проверяется здесь, а им оно только
помешало бы.

4. РУЧНОЙ ПРОГОН: ЛИМИТ НЕ ПРЕВЫШАЕТСЯ
------------------------------------------------------------------------------

Задать лимит:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE provider_rate_limits SET limit_per_minute = 5;"
    docker compose exec db psql -U gamer -d gamer_market -c \
      "DELETE FROM provider_calls;"

Создать десять оплаченных заказов и подождать полминуты. Затем посмотреть,
сколько обращений было в каждом окне:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT c.provider, max(w.calls) AS пик
         FROM provider_calls c
         JOIN LATERAL (
              SELECT count(*) AS calls FROM provider_calls x
               WHERE x.provider = c.provider
                 AND x.called_at > c.called_at - interval '1 minute'
                 AND x.called_at <= c.called_at
         ) w ON true
        GROUP BY c.provider;"

Пик обязан быть не больше пяти. Запрос двигает окно по каждому обращению —
именно в эти моменты счёт и может вырасти.

Журнал перед проверкой очищается не случайно: запрос считает по всей истории
и не знает, что лимит менялся. Оставь в журнале обращения, сделанные при
лимите 60, — и пик покажет шестьдесят, что выглядит нарушением лимита 5,
хотя нарушения не было. По той же причине bin/surge первым делом очищает
журнал.

Вернуть лимит:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE provider_rate_limits SET limit_per_minute = 60;"

5. РУЧНОЙ ПРОГОН: НИЧЕГО НЕ ТЕРЯЕТСЯ
------------------------------------------------------------------------------

Пока лимит исчерпан, задачи стоят в очереди с причиной rate_limited:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT status, attempts, last_error, run_at::time(0)
         FROM jobs WHERE last_error = 'rate_limited' ORDER BY id DESC LIMIT 5;"

Ожидается status pending и attempts 0: обращения не было, попытка
не засчитана. Именно поэтому всплеск не приводит к проваленным задачам.

Позиции при этом остаются в прежнем состоянии, а не уходят в отказ:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT status, count(*) FROM order_items
        WHERE settled_at IS NULL GROUP BY status;"

Проваленных задач быть не должно:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT count(*) FROM jobs WHERE status = 'failed';"

6. РУЧНОЙ ПРОГОН: ПРИОРИТЕТ ОПЛАЧЕННЫХ
------------------------------------------------------------------------------

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT priority, status, count(*) FROM jobs
        GROUP BY priority, status ORDER BY priority DESC;"

Задачи выдачи по оплаченным заказам имеют приоритет 100. Очередь выбирается
оператором ORDER BY priority DESC, run_at, id — при равном приоритете
побеждает тот, кто ждёт дольше.

Проверить порядок выборки:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT id, priority, payload->>'order_id' AS заказ
         FROM jobs WHERE status = 'pending' AND run_at <= now()
        ORDER BY priority DESC, run_at, id LIMIT 5;"

Это тот же порядок, которым берёт задачи исполнитель.

Запрос имеет смысл только при непустой очереди: запусти bin/surge в одном
окне, а его — в другом. На разобранной очереди он вернёт ноль строк, и это
не признак поломки.

7. РУЧНОЙ ПРОГОН: ПРОГРЕСС
------------------------------------------------------------------------------

    curl -s http://localhost:8080/api/admin/queue | python3 -m json.tool

    docker compose exec app php bin/queue
    docker compose exec app php bin/queue --watch --interval=2

Наблюдать имеет смысл во время работы bin/surge из другого окна: тогда видно,
как очередь убывает ступенями по мере освобождения окна, а не равномерно.

Что показывают поля:

    queue.pending      задачи, готовые к выдаче прямо сейчас
    queue.deferred     отложенные до срока: ждут места в лимите
    queue.paid_ahead   сколько из ожидающих — оплаченные заказы
    items.awaiting     позиции оплаченных заказов, по которым покупатель ждёт
    items.unpaid       позиции неоплаченных заказов: в очередь не попадают
                       и квоту поставщика не расходуют
    providers.used     занято мест в текущем окне
    throughput.eta     оценка сверху: сколько ждать разбора очереди
