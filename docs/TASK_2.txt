ЗАДАЧА 2
Поставщик, которому нельзя доверять
------------------------------------------------------------------------------

Требование: поставщик может втихую выдать один код дважды, отдать чужой код
или ответить ошибкой, хотя код на самом деле выдал. Ответу верить нельзя.
Гарантировать нужно самим: покупатель получает ровно один рабочий код,
один код не уходит двум покупателям, расхождения разбираются автоматически.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Раздел 3 — воспроизводимый скрипт.
Разделы 4-8 — ручной прогон сценариев.

Все команды выполняются из корня проекта при поднятом окружении.
После изменения кода выдачи обязателен перезапуск фоновых процессов:

    docker compose restart worker scheduler


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Приёмка кода
~~~~~~~~~~~~

До этой задачи ответ поставщика принимался на веру: что прислал, то и уходило
покупателю. Теперь между «поставщик прислал код» и «код принадлежит заказу»
стоит приёмка.

    CREATE TABLE issued_codes (
        code text PRIMARY KEY,
        provider text, request_id text,
        order_id text, position integer,
        accepted_at timestamptz
    );
    CREATE UNIQUE INDEX issued_codes_request_idx ON issued_codes (provider, request_id);

Два ограничения делают всю работу:

    PRIMARY KEY (code)             один код физически не ляжет в два заказа
    UNIQUE (provider, request_id)  один запрос физически не даст двух кодов

Код уникален глобально, а не в пределах поставщика. Для цифрового товара
строка кода и есть сам товар: если два поставщика прислали одну строку, товар
всё равно один, и уйти в два заказа он не может.

Проверка «а нет ли уже такого кода» перед вставкой не дала бы ничего: между
чтением и записью вклинивается конкурент. Здесь же вставка либо проходит,
либо нарушает ограничение — и второй случай разбирается.

Четыре исхода приёмки:

    accepted   код принят, до этого он никому не принадлежал
    repeat     тот же код по тому же запросу: повтор, ничего не изменилось
    duplicate  код уже принадлежит другой позиции — поставщик выдал его дважды
               либо прислал чужой
    conflict   по тому же запросу поставщик прислал другой код; принятым
               остаётся первый, он уже мог уйти покупателю


Поколение запроса
~~~~~~~~~~~~~~~~~

    req_<заказ>_<позиция>_<поставщик>_g<поколение>

request_id детерминирован, поэтому повтор получает от поставщика тот же код —
обычно это защита. Но если код отклонён приёмкой как чужой, тот же request_id
будет возвращать его вечно. Поколение — единственный способ запросить другой
код у того же поставщика.

Поколение растёт только при отклонении, а не при повторе. Обычный повтор
после сбоя или таймаута идёт с прежним номером, иначе занял бы у поставщика
второй код.

Если поставщик исчерпал попытки и каждый раз присылал чужой код, состояние
его известно: выдачи, принадлежащей нам, не было. Значит переключение на
резервного допустимо — в отличие от молчания, откуда переключаться нельзя.


Проверка отрицательного ответа
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Отказ — заявление, состояние на стороне поставщика — факт, и расходятся они
регулярно. Поставщик занял код и ответил ошибкой: по ответу кода нет,
по складу есть.

Поэтому у поставщика появился второй метод:

    GET /stubs/provider-{a|b}/status?request_id=...

    {"status": "issued", "code": "..."}   выдал
    {"status": "not_issued"}              не выдавал
    503                                   ответить не может

Он вызывается в двух местах:

    - сразу после отрицательного ответа на выдачу, до переключения
      на резервного поставщика;
    - после того, как исчерпаны повторы и ответа так и не было.

Если состояние говорит «выдал» — код принимается, позиция доводится до выдачи,
расхождение записывается и тут же закрывается.

Отсюда важное следствие: молчание поставщика больше не оставляет позицию
в неопределённости, если его состояние доступно. Неразрешённой она остаётся
только при полной недоступности — когда правду узнать не у кого. Для этого
в заглушке есть отдельный режим blackout.


Журнал расхождений
~~~~~~~~~~~~~~~~~~

Разбор идёт автоматически, но факт должен оставаться видимым: без журнала
система молча исправлялась бы, и понять, кому из поставщиков нельзя верить,
было бы не по чему.

    duplicate_code     код уже принадлежит другой позиции
    request_conflict   по тому же запросу прислан другой код
    silent_issue       ответил отказом или промолчал, но код выдал

Строка появляется при обнаружении и закрывается при разборе. Повторное
обнаружение того же факта не плодит строк — за этим следит уникальный индекс
на (provider, request_id, kind, code).


Сверка с поставщиками
~~~~~~~~~~~~~~~~~~~~~

AuditProviderCodes идёт от незавершённых позиций, по которым уже было
обращение с неопределённым или отрицательным исходом, и по каждой спрашивает
состояние поставщика. Если код выдан — принимает и возвращает позицию
в очередь.

Закрывает и расхождения, которые разрешились сами: позиция выдана другим
поставщиком либо деньги возвращены.

Запускается планировщиком раз в минуту вместе с доводкой:

    docker compose exec app php bin/heal --verbose

Все действия идемпотентны: приёмка защищена ограничениями таблицы, повторный
запуск ничего не удваивает.


Режимы недобросовестности заглушки
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

    duplicate_code    отдаёт код, уже выданный по другому запросу;
                      склад при этом не расходуется
    foreign_code      отдаёт код другого поставщика — товар,
                      которым не распоряжается
    error_but_issued  занимает код и отвечает отказом
    blackout          занимает код и не отвечает ни на выдачу,
                      ни на запрос состояния

Задаются тем же служебным маршрутом, что и прежние:

    curl -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"duplicate_code"}'

2. АВТОМАТИЧЕСКИЕ ТЕСТЫ
------------------------------------------------------------------------------

    docker compose exec app ./vendor/bin/phpunit

Относящиеся к задаче:

    docker compose exec app ./vendor/bin/phpunit --filter DishonestProviderTest
    docker compose exec app ./vendor/bin/phpunit --filter ProviderFailoverTest

Что проверяется в DishonestProviderTest:

    дубль не попадает во второй заказ        код остаётся у первого,
                                             второй обслуживает резервный
    чужой код отклоняется                    принятый код не меняет владельца
    ошибка при выданном коде                 код найден запросом состояния,
                                             выдал тот же поставщик
    молчание разрешается состоянием          на резервного не переключились,
                                             второго кода не занято
    полная недоступность                     позиция остаётся unresolved,
                                             непроверенный код не принят
    повтор после ошибки                      второй выдачи нет
    расхождения фиксируются и закрываются    открытых не остаётся
    сверка находит код после обрыва          выдан ранее занятый код
    повторная сверка                         ничего не меняет
    приёмка различает повтор и конфликт      подменённый код не принят
    отчёт сверки                             показывает расхождения по родам

3. ВОСПРОИЗВОДИМЫЙ СКРИПТ
------------------------------------------------------------------------------

    docker compose exec app php bin/dishonest

Четыре сценария, по одному на каждое требование задачи. Ненулевой код
возврата означает нарушение.

    duplicate  поставщик прислал уже выданный код
    foreign    поставщик прислал чужой код
    silent     ответил ошибкой, но код выдал
    audit      обрыв после выдачи, сверка разбирает сама

Отдельный сценарий и повторы:

    docker compose exec app php bin/dishonest --scenario=silent
    docker compose exec app php bin/dishonest --repeat=3

Ожидаемый вывод:

    ── поставщик прислал уже выданный код
       1/1  ок   {"первый":"A-ea7f2e7f3a","второй":"B-7997cb97c0",
                  "поставщик":"b","расхождения":["duplicate_code"]}

    ── ответил ошибкой, но код выдал
       1/1  ок   {"код":"A-536a7ab61c","поставщик":"a","занято_у_A":1,
                  "расхождения":["silent_issue"]}

    Проверок: 20, нарушений: 0

Товар со своим складом скрипт готовит сам: KEY-DISHONEST, по десять кодов
у каждого поставщика. Сценарии не зависят от остальных данных базы.

4. РУЧНОЙ ПРОГОН: ОДИН КОД НЕ УХОДИТ В ДВА ЗАКАЗА
------------------------------------------------------------------------------

Первый заказ обслуживается честно:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"ok"}'
    curl -s -X POST http://localhost:8080/stubs/provider-b/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"error"}'

    FIRST=$(curl -s -X POST http://localhost:8080/api/orders \
      -H 'Content-Type: application/json' -d '{"sku":"KEY-GTA5"}' \
      | python3 -c 'import sys,json; print(json.load(sys.stdin)["order_id"])')

    curl -s -X POST http://localhost:8080/api/webhooks/payment \
      -H 'Content-Type: application/json' \
      -d "{\"event_id\":\"evt_$RANDOM\",\"order_id\":\"$FIRST\",
           \"status\":\"paid\",\"amount\":1990,\"currency\":\"RUB\",
           \"created_at\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}"

Теперь A присылает всем один и тот же код, а B поднимается резервным:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"duplicate_code"}'
    curl -s -X POST http://localhost:8080/stubs/provider-b/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"ok"}'

Второй заказ создаётся и оплачивается той же парой команд с переменной SECOND.
Через несколько секунд:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT order_id, position, provider, code FROM issued_codes
        WHERE order_id IN ('$FIRST', '$SECOND') ORDER BY accepted_at;"

Ожидается: два разных кода, второй выдан поставщиком b. Код первого заказа
принадлежит ровно одной позиции — приёмка отклонила дубль.

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT kind, provider, resolution FROM provider_discrepancies
        WHERE order_id = '$SECOND';"

Ожидается строка duplicate_code.

Попытка занять принятый код вручную под другой заказ:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "INSERT INTO issued_codes (code, provider, request_id, order_id, position)
       SELECT code, 'a', 'req_ручной', '$SECOND', 1 FROM issued_codes
        WHERE order_id = '$FIRST';"

Ожидается ошибка duplicate key value violates unique constraint. Один код
в двух заказах невозможен независимо от кода приложения.

5. РУЧНОЙ ПРОГОН: ОШИБКА ПРИ ВЫДАННОМ КОДЕ
------------------------------------------------------------------------------

Поставщик занимает код и отвечает отказом, резервный выключен:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"error_but_issued"}'
    curl -s -X POST http://localhost:8080/stubs/provider-b/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"error"}'

Заказ и оплата — теми же командами, что в разделе 4, переменная LIAR.
Через несколько секунд:

    curl -s http://localhost:8080/api/orders/$LIAR | python3 -m json.tool

Ожидается delivered с кодом, хотя поставщик отвечал ошибкой. Код найден
запросом состояния.

Что видно в попытках и расхождениях:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT provider, outcome, reason FROM delivery_attempts
        WHERE order_id = '$LIAR' ORDER BY id;"

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT kind, details, resolution FROM provider_discrepancies
        WHERE order_id = '$LIAR';"

Ожидается silent_issue с пометкой «ответ provider_unavailable, код выдан»
и разбором «код принят по состоянию поставщика».

Повтор выдачи второй выдачи не создаёт:

    docker compose exec -e ORDER=$LIAR app php -r '
      $c = require "/app/src/bootstrap.php";
      var_dump(($c->get(App\Services\DeliverOrderItem::class))(getenv("ORDER"), 1));'

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT count(*) FROM provider_stock WHERE request_id LIKE '%$LIAR%';"

Ожидается noop и ровно один занятый код.

6. РУЧНОЙ ПРОГОН: ПРОВЕРКА СОСТОЯНИЯ ПОСТАВЩИКА
------------------------------------------------------------------------------

Тот же метод можно вызвать напрямую:

    REQ=$(docker compose exec -T db psql -U gamer -d gamer_market -tA -c \
      "SELECT request_id FROM issued_codes WHERE order_id = '$LIAR';")

    curl -s "http://localhost:8080/stubs/provider-a/status?request_id=$REQ" \
      | python3 -m json.tool

Ожидается issued и тот же код, что у заказа.

По несуществующему запросу:

    curl -s "http://localhost:8080/stubs/provider-a/status?request_id=req_НЕТ" \
      | python3 -m json.tool

Ожидается not_issued.

При полной недоступности состояние не отдаётся вовсе:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"blackout"}'

    curl -s -o /dev/null -w '%{http_code}\n' \
      "http://localhost:8080/stubs/provider-a/status?request_id=$REQ"

Ожидается 503. Для вызывающей стороны это отсутствие ответа, а не
отрицательный ответ: именно поэтому позиция остаётся в unresolved, а не
уходит в возврат.

Верни режим обратно:

    curl -s -X POST http://localhost:8080/stubs/provider-a/behavior \
      -H 'Content-Type: application/json' -d '{"mode":"ok"}'

7. РУЧНОЙ ПРОГОН: АВТОМАТИЧЕСКИЙ РАЗБОР
------------------------------------------------------------------------------

Сценарий воспроизводится скриптом целиком:

    docker compose exec app php bin/dishonest --scenario=audit

Вручную: у поставщика код числится выданным по нашему запросу, у нас о нём
ничего нет — состояние после обрыва процесса сразу за ответом поставщика.

Сверка запускается вместе с доводкой:

    docker compose exec app php bin/heal --verbose

Ожидается ненулевое «восстановлено кодов». После обработки очереди позиция
выдана тем же кодом, который поставщик занял раньше, второго кода не появилось.

Состояние расхождений по всей системе:

    docker compose exec app php bin/reconcile | sed -n '/Расхождения/,/^$/p'

Ожидается перечень родов с числом обнаруженных и открытых:

    duplicate_code   всего 24, открыто 0
    silent_issue     всего 8,  открыто 0

Открытых быть не должно: разбор идёт без участия человека. Ненулевое
«открыто» означает расхождение, которое сверка разобрать не смогла, —
оно попадает в отчёт отдельным разделом.

8. РУЧНОЙ ПРОГОН: КОДЫ В ОБХОД ПРИЁМКИ
------------------------------------------------------------------------------

Отчёт сверки отвечает и на вопрос, не ушёл ли покупателю код, который приёмка
своим не признавала:

    docker compose exec app php bin/reconcile | grep 'в обход'

Ожидается ноль. Непустой список означал бы путь, которым ответ поставщика был
принят на веру, — то есть возврат к поведению до этой задачи.

Проверить можно и напрямую:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "SELECT d.order_id, d.position, d.code
         FROM deliveries d
        WHERE d.status = 'delivered' AND d.code IS NOT NULL
          AND NOT EXISTS (SELECT 1 FROM issued_codes c
                           WHERE c.code = d.code
                             AND c.order_id = d.order_id
                             AND c.position = d.position);"

Ожидается пустой результат.
