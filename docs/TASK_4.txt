ЗАДАЧА 4
Восстановление картины на любой прошлый момент
------------------------------------------------------------------------------

Требование: по истории операций восстанавливается точное состояние заказа
и денег на любой прошлый момент. История только дополняется, задним числом
ничего не переписывается. Итоги за период считаются из этой истории и сходятся.

Раздел 1 — что сделано.
Раздел 2 — автоматические тесты.
Раздел 3 — команда.
Разделы 4-7 — ручной прогон.

Все команды выполняются из корня проекта при поднятом окружении.


==============================================================================
1. ЧТО СДЕЛАНО
------------------------------------------------------------------------------

Почему одного текущего состояния не хватает
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Статус заказа лежит в orders.status и перезаписывается при каждом изменении.
Прежнее значение затирается, и вопрос «в каком состоянии был заказ вчера
в полдень» остаётся без ответа.

С деньгами иначе: журнал проводок изначально ведётся дополнением, и остаток
на момент — это сумма движений до этого момента. Отдельная история для денег
не нужна, нужен только запрос.

Поэтому добавлена история состояний и не добавлено ничего для денег.


Журнал событий
~~~~~~~~~~~~~~

    CREATE TABLE order_events (
        id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
        order_id text NOT NULL,
        position integer,          -- NULL: событие заказа целиком
        from_status text,
        to_status text NOT NULL,
        amount_minor bigint,
        occurred_at timestamptz NOT NULL DEFAULT now()
    );

Цена пишется в событие, а не берётся из текущей строки: по истории должно
восстанавливаться и состояние, и деньги, не обращаясь к тому, что есть сейчас.

Два разных времени, и путать их нельзя:

    occurred_at   когда событие случилось — по нему восстанавливается картина
    id            в каком порядке записано — по нему сверяется текущее
                  состояние с последним записанным событием


Историю пишет база
~~~~~~~~~~~~~~~~~~

    CREATE TRIGGER orders_history
        AFTER INSERT OR UPDATE ON orders
        FOR EACH ROW EXECUTE FUNCTION log_order_change();

    CREATE TRIGGER order_items_history
        AFTER INSERT OR UPDATE ON order_items
        FOR EACH ROW EXECUTE FUNCTION log_order_item_change();

Не сервис, а триггер. Сервис можно забыть дополнить, добавляя новый путь
изменения статуса, и история молча разойдётся с состоянием — а обнаружится
это через месяц, когда понадобится разбор. Триггер срабатывает на любое
изменение, откуда бы оно ни пришло, включая запрос из psql.

Событие пишется только при смене статуса: UPDATE, не меняющий значение,
истории не добавляет.


Запрет переписывания
~~~~~~~~~~~~~~~~~~~~

    CREATE FUNCTION forbid_rewrite() RETURNS trigger AS $$
    BEGIN
        RAISE EXCEPTION 'История только дополняется: % запрещён для таблицы %',
            TG_OP, TG_TABLE_NAME;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER order_events_append_only
        BEFORE UPDATE OR DELETE ON order_events ...
    CREATE TRIGGER ledger_entries_append_only
        BEFORE UPDATE OR DELETE ON ledger_entries ...

«Только дополняется» — свойство таблицы, а не договорённость между
разработчиками. Договорённость нарушается ошибкой, ограничение не нарушается
никак: UPDATE и DELETE отбиваются, кто бы их ни выполнял.

Журнал денег дополнялся и раньше, но запрета не было — теперь есть.


Восстановление состояния
~~~~~~~~~~~~~~~~~~~~~~~~

Состояние позиции на момент — это последнее событие по ней до этого момента:

    SELECT DISTINCT ON (position) position, to_status, amount_minor
      FROM order_events
     WHERE order_id = ? AND position IS NOT NULL AND occurred_at <= ?
     ORDER BY position, occurred_at DESC, id DESC

Момент задаётся включительно: событие, случившееся ровно в указанное время,
в состояние входит. Иначе граница периода принадлежала бы обоим периодам
сразу либо ни одному.

Код позиции показывается, только если он был принят к тому моменту
(issued_codes.accepted_at <= момент): выданное позже вчерашним числом
не показывается.

Доли секунды сохраняются на всём пути. Внутри одной секунды заказ успевает
пройти несколько состояний, и округление показало бы картину не того момента,
о котором спрашивали.


Итоги за период
~~~~~~~~~~~~~~~

    остаток на начало   движения до начала периода
    движения за период  движения внутри периода
    остаток на конец    движения до конца периода

Проверка: остаток на конец обязан равняться остатку на начало плюс движения.
Если равенство не выполняется, значит в журнал вмешались задним числом —
а вмешаться в него нельзя.

Вторая проверка: движения за период сами по себе дают в сумме ноль. Каждая
проводка состоит из строк, дающих ноль, и период режет проводки целиком —
обе строки записаны одной транзакцией.


Сверка состояния с историей
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Отчёт сверки получил четвёртый вопрос: совпадает ли текущее состояние
с последним записанным событием.

    расхождений с историей  0

Ноль означает, что ни одно изменение не прошло мимо журнала. Единственный
способ получить расхождение — отключить триггер, что и проверяется тестом.

2. АВТОМАТИЧЕСКИЕ ТЕСТЫ
------------------------------------------------------------------------------

    docker compose exec app ./vendor/bin/phpunit --filter HistoryTest

Что проверяется:

    состояние заказа на момент        до выдачи paid и pending без кода,
                                      после — delivered с кодом
    до создания заказа нет ничего     запрос возвращает пусто, а не ошибку
    деньги на момент                  после оплаты выдано ноль, обязательство
                                      равно сумме; после выдачи наоборот
    частичная выдача по шагам         на середине заказ ещё delivering,
                                      возврата ещё нет
    история только дополняется        UPDATE и DELETE по order_events
                                      и ledger_entries отбиваются
    историю пишет база                прямой UPDATE из psql тоже попадает
                                      в журнал
    смена статуса на тот же           событий не добавляет
    итоги за период сходятся          на конец = на начало + движения
    периоды стыкуются                 сумма частей равна целому
    состояние совпадает с историей    расхождений нет, отчёт здоров
    расхождение обнаруживается        изменение с отключённым триггером
                                      находится сверкой
    лента событий                     полный путь заказа по порядку
    состояние по HTTP                 GET /api/admin/history/orders/{id}?at=
    деньги и итоги по HTTP            /money?at=, /period?from=&to=
    неверный момент                   400 invalid_request

3. КОМАНДА
------------------------------------------------------------------------------

    php bin/history --order=ord_... --timeline
    php bin/history --order=ord_... --at='2026-09-10 12:00:00'
    php bin/history --money --at='2026-09-10 12:00:00'
    php bin/history --period --from='2026-09-10' --to='2026-09-11'

Ключ --json отдаёт то же в машиночитаемом виде. Для --period ненулевой код
возврата означает, что итоги не сошлись.

То же самое по HTTP:

    GET /api/admin/history/orders/{id}?at=...
    GET /api/admin/history/money?at=...
    GET /api/admin/history/period?from=...&to=...

Без параметра at отдаётся текущая картина.

4. РУЧНОЙ ПРОГОН: ПУТЬ ЗАКАЗА
------------------------------------------------------------------------------

Свежий заказ с частичной выдачей создаёт сценарный скрипт:

    docker compose exec app php bin/partial --scenario=partial

    ORDER=$(docker compose exec -T db psql -U gamer -d gamer_market -tA -c \
      "SELECT id FROM orders WHERE status = 'partially_delivered'
        ORDER BY created_at DESC LIMIT 1;")

    docker compose exec -e ORDER=$ORDER app php bin/history --order=$ORDER --timeline

Ожидается полный путь, включая повторы по невыданной позиции:

    заказ      —            -> created
    позиция 1  —            -> pending
    позиция 2  —            -> pending
    позиция 3  —            -> pending
    заказ      created      -> paid
    позиция 1  pending      -> delivering
    заказ      paid         -> delivering
    позиция 1  delivering   -> delivered
    позиция 2  delivering   -> out_of_stock
    позиция 2  out_of_stock -> delivering
    позиция 2  delivering   -> out_of_stock
    позиция 2  out_of_stock -> refunded
    заказ      delivering   -> partially_delivered

Три захода по второй позиции видны как есть: история не сглаживает.

5. РУЧНОЙ ПРОГОН: СОСТОЯНИЕ НА МОМЕНТ
------------------------------------------------------------------------------

Взять точное время выдачи первой позиции:

    MOMENT=$(docker compose exec -T db psql -U gamer -d gamer_market -tA -c \
      "SELECT occurred_at FROM order_events
        WHERE order_id = '$ORDER' AND position = 1 AND to_status = 'delivered';")

    docker compose exec app php bin/history --order=$ORDER --at="$MOMENT"

Ожидается картина именно того мгновения:

    состояние                    delivering
    Позиции:
      1  delivered      1990     PART-95ffc256cf
      2  delivering     500
      3  pending        1990
    Деньги по заказу:
      оплачено 448000, выдано 199000, возвращено 0, в работе 249000, сходится да

Первая позиция уже с кодом, третья ещё не начата, деньги отражают ровно
этот момент. Сравнить с текущим состоянием:

    docker compose exec app php bin/history --order=$ORDER

Разница между двумя выводами и есть то, что произошло за эти секунды.

6. РУЧНОЙ ПРОГОН: ИСТОРИЮ НЕ ПЕРЕПИСАТЬ
------------------------------------------------------------------------------

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE order_events SET to_status = 'подделка' WHERE id = 1;"

    docker compose exec db psql -U gamer -d gamer_market -c \
      "DELETE FROM ledger_entries WHERE id = 1;"

Ожидается в обоих случаях:

    ERROR:  История только дополняется: UPDATE запрещён для таблицы order_events

Отказ приходит суперпользователю, выполняющему запрос вручную. Это и есть
разница между договорённостью и ограничением.

Изменение в обход сервисов при этом попадает в историю:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE order_items SET status = 'delivering'
        WHERE order_id = '$ORDER' AND position = 1;"

    docker compose exec app php bin/history --order=$ORDER --timeline | tail -3

Последним событием будет delivered -> delivering, записанное триггером.
Вернуть как было:

    docker compose exec db psql -U gamer -d gamer_market -c \
      "UPDATE order_items SET status = 'delivered'
        WHERE order_id = '$ORDER' AND position = 1;"

В истории останутся оба события: она не переписывается, а дополняется.

7. РУЧНОЙ ПРОГОН: ИТОГИ ЗА ПЕРИОД
------------------------------------------------------------------------------

    docker compose exec app php bin/history --period \
      --from='2026-09-10 18:00:00+00' --to='2026-09-11 07:00:00+00'

Ожидается:

    на начало:  оплачено 158077000, выдано 153230000, возвращено 4847000
    за период:  оплачено   6617000, выдано   6567000, возвращено   50000
    на конец:   оплачено 164694000, выдано 159797000, возвращено 4897000

    остаток на конец = на начало + движения      да
    движения за период сбалансированы            да

158077000 + 6617000 = 164694000. Проверить можно любым разбиением: сумма
итогов двух смежных периодов равна итогу целого.

Сверка состояния с историей:

    docker compose exec app php bin/reconcile | grep 'с историей'

Ожидается ноль. Ненулевое значение означает изменение, прошедшее мимо
журнала, — и разобрать его придётся вручную, потому что автоматически
восстановить затёртое прошлое неоткуда.
